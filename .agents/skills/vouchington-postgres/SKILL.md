# Vouchington PostgreSQL queries

Load `postgres-node-performance-tuning`, `postgres-schema-design`, `postgres-locking`, `postgresql-rules` first.

Schema and migration rules live in [`backend/data-stores/psql/AGENTS.md`](../../../backend/data-stores/psql/AGENTS.md).

## Connections and transactions

- Use `read()` (replica), `write()` (primary), and `beginTransaction()` from `@data-stores/psql`; services never own a pool. Read-after-write and locking reads use `write()` or the active transaction.
- Newly owned transactions use `await using` from `@vouchington/postgres`; `withTransactionOptions` only joins a client already in a transaction. Joining or opening on a **borrowed** client needs the live `SAVEPOINT`/`RELEASE SAVEPOINT` probe (`25P01` means idle; rethrow anything else, including `25P02`) through raw `client.query`. Never swap it for `getTransactionStatus()`, and never patch `pg` ([why](../../../docs/development/postgresql/reference-transactions.md)).
- Lock scope: a transaction locks only the rows it writes, never its parent or ancestors, thread root, community, or membership sets. That covers row locks, advisory locks, and lock helpers. Caps and "last X" guards check a capped count and then write: no lock, counter row, slot table, or admission-only constraint; overshoot is accepted. A membership-grant cap counts committed grants; do not use SERIALIZABLE to make it strict, and return a conflict only when an activation or effective-membership uniqueness invariant rejects a write.
- Privacy, legal, and irreversible-side-effect races (user deletion, legal holds, external deletes) may lock the aggregate root (`users`) even when unwritten; a transaction that also updates it takes `FOR NO KEY UPDATE` first. Write skew that must hold (an administrator keeping MFA) runs the guard read and the write in one SERIALIZABLE transaction and returns 409 on `40001`, with no retry. Decline automated "race" findings that ask for locks on read context.
- Adding any lock is an owner decision: the PR body names the corrupting interleaving and why a constraint, conditional write, in-statement guard, or SERIALIZABLE+409 does not fit; unattended agents ship the lock-free design and propose the lock in the PR body. Tests assert final state, never that a lock was taken.
- Automated-review "race" findings asking for a lock, wider lock, or generation/fence/claim/counter column are declined, answering with the first of: constraint, conditional write, in-statement guard, SERIALIZABLE+409, or "accepted: best effort" with the worst case.
- After relaxing a single-row assumption, audit stale `LIMIT 1` sites.
- Get-or-create on identity-backed lookup tables reads first and inserts only on a miss; for a writer-side reconciliation use `MERGE` or an advisory lock plus a primary re-check.

## Query shape

- Query UUIDv7 `id`, never `created_at`; annotate queries with `/* functionName */`, use cursors instead of `OFFSET`, and use `pgvector.toSql()`. Query partition parents except for operator maintenance and bounded DEFAULT retention, and constrain the partition key ([pruning](../../../docs/overview/architecture/partition-pruning-hints.md)). Partition by the dominant access key; `RANGE(id)` only when every hot reader carries an id or time bound.
- Time windows compare the raw `id` against `getMinUUIDv7ForDate` bounds. Never extract timestamps from `id` in a predicate, and never bound ids with the volatile `uuidv7(...)`; pass a TypeScript-computed bound or a STABLE inlinable helper.
- Name table columns explicitly (no `SELECT *`, `alias.*`, `RETURNING *`); a view may be read with `*`.
- Use the simplest correct query (plain `WHERE`/`EXISTS` first). Added complexity (CTE, `UNION` candidates, `LATERAL`, `MATERIALIZED`/planner fences, `GROUP BY`/`DISTINCT` dedupe, `HAVING COUNT(*) = n`, extra cursor state) needs `EXPLAIN ANALYZE` and a benchmark against that simpler query at representative cardinality, shown in the PR. Toy-sized data and comparisons with old main do not count. A failed gate sends you to the simpler query first; never widen a gate. Quote owner decisions verbatim in issues and PRs. A materialized prefix is an optimizer fence, so its own read bound must hold.
- A list or feed read is one walk over the listed entity (or the membership index joined to targets, for saved posts and list items), eligibility in `WHERE`, and a keyset cursor matching every ordering key. No candidate pools: no capped or `MATERIALIZED` CTE of the listed entity filtered later, no window loops or probes, no cursor proof state, no config field sizing a pool, no new write caps. Vector search is the exception: it may bound its candidates with an HNSW k-nearest prefix (`ORDER BY embedding <=> query LIMIT k`), with `k` a `DynamicConfig` field that has a hard maximum, gated by an explain-analyze scenario (this is how vector search is bounded, not a filtered pool of the listed entity). Where a filter can reject long runs (blocks, mutes), the time window is the scan bound and EXPLAIN compares rows read with rows returned. A short or empty page needs a continuation cursor and a "load more" signal. Small viewer-scoped sets (follows, mutes, blocks, memberships) may be subqueries or semi-joins.
- Bound inputs: cap filter terms (for example `#slug` terms per query, ANDed, same validation error in REST and MCP), then walk an index with per-row `EXISTS` probes, an inspected-row cap, and a cursor. Do not cap product data (aliases per topic) to make a query cheap. Each cap is a `DynamicConfig` field with a default and a hard maximum, and the SQL binds the hard maximum.
- Counts: displayed counts are capped counts (`LIMIT cap + 1` plus a `capped` flag). Non-personalized trending lists are materialized views over a bounded window with an explain-analyze scenario; personalized variants query the view and join live eligibility (deleted, removed, hidden, disabled). A stored, indexed per-row score such as the post hot score stays an index walk. A ranking by an unbounded count is a materialized view indexed `(count DESC, id DESC)` refreshed on a schedule, never a counter column. No periodic recount.
- Read `view_*` only by key: pick ids from indexed base tables, then read the view by those ids; never filter, sort, page, or count on view columns. Pull-up needs a flat `SELECT` with no top-level `WITH` and no plain `UNION` (`UNION ALL` is fine); otherwise the view is an unindexed subplan per outer row. Restrict correlated views at every nesting level: candidate-bind (indexed subselect, `UNION ALL` sources, join to base table and eligibility view in one scope) with the shared builders in [`@modules/feed-query-builders`](../../../docs/overview/architecture/backend/README.md). A scalar subquery with `LIMIT 1` is never hashed; an `EXISTS` over an eligibility view inside `OR` can be. Nest user data via a scalar subquery to `view_embedded_users`, never `LEFT JOIN view_users_public`. Views never expose hashes, embeddings, or search vectors. Write managed views as `CREATE OR REPLACE VIEW name AS SELECT ...;` without outer parentheses (Squawk); a replaced materialized view is dropped first with `squawk-ignore ban-drop-view`.
- Direct topic reads preserve both active-topic filters. Reference readers keep the deletion filter; omit the merge filter only when the merge repoints or removes that reference. History and authorization checks keep it.
- Retained identities (ids kept after a delete) never authorize the deleted entity.
- Elections are parent-identified tallies (`election.id === parent.id`); reference the parent. Aggregate/STORED numeric filters match SQL types; reuse [`buildVoteScoreFilters`](../../../backend/services/entity-relations/vote-score-filters.mts).

## Indexes

- A measured index fix needs no separate approval; keep it in the query's PR with before/after plans.
- Prefix autocomplete uses a `COLLATE "C"` btree index with `COLLATE "C"` range bounds, `ORDER BY`, and keyset cursor, gated on the index, bounds, and `noSort: true`; `text_pattern_ops` serves neither `ORDER BY` nor `ILIKE`.
- Recheck an index change's dependent queries with the [EXPLAIN ANALYZE harness](../../../docs/prompts/scheduled/postgresql-explain-analyze.md) and add or update scenarios and plan gates under `backend/scripts/explain-analyze/`.
