## Implementation Rules

- **Journal friction as it happens**: during implementation, write each contemporaneous note — friction, failed approaches, decisions, no-mistakes/tooling usage, and every observed GitHub Actions failure signature and outcome — using [blackboard](../blackboard/SKILL.md). See its [mandatory journal triggers](../blackboard/SKILL.md#mandatory-journal-triggers) for the named moments that require a note immediately rather than at session end. A same-session or later [retrospective](../retrospective/SKILL.md) reads this journal as its primary source for transcript-dependent sections, instead of reconstructing them from memory at the end.
- **Shepherd Journal preservation is durable by construction**: `node dev/pr-description.mts update <pr>` preserves the exact live canonical `<details>` Shepherd Journal block (or historical `## Shepherd Journal` section) when omitted. Legacy-to-details migration is accepted only when every live entry survives; malformed, ambiguous, or details-to-H2 supplied bodies fail closed. See [pr-description](../pr-description/SKILL.md).
- After plan acceptance, the orchestrator dispatches bounded implementation and follow-up fixes to the Codex `implementation` agent or a Claude Code general-purpose Sonnet subagent. The orchestrator remains responsible for sequencing, resolving conflicts between results, and final validation. Run write agents serially within a worktree to avoid races on the Git index, lockfiles, and shared build or test caches; parallelize only read-only agents.
- For accepted-plan work, keep an implementation ledger until the first push. Each row should map `accepted decision or named surface -> target files/tests -> implementation/delegation owner -> evidence status`. Include plan decisions that are easy to lose during coding, such as partition keys, delegation boundaries, authorization tiers, parity surfaces, fixture responsibilities, queue payload sources, and read-after-write data sources. Before pushing, every row must either have evidence from [Before Pushing](before-pushing.md) or an explicit reason it is out of scope.
- When resolving a rebase conflict, treat it as a semantic review instead of a text merge. Inspect the conflict stages against refreshed origin/main, state the upstream invariant being preserved in the implementation ledger or PR notes, and integrate the upstream changes with the changes from this PR. If upstream changed the same lifecycle, authorization, moderation, deletion, queue, or parity surface, update the implementation ledger and rerun the targeted tests or searches for that invariant before pushing.
- When multiple agents share one worktree, the root coordinator serializes DB/Valkey-backed test commands (`requiresWebInit` Vitest projects, web integration, Playwright, and coverage runs that include those suites). The worktree database and Valkey containers are shared process resources, so parallel consumers can contend even when each individual test file is isolated.
- **Pre-authoring size check**: before authoring or significantly extending a file, check its current size with `wc -l <file>` (for source/test files) or `wc -c <file>` (for `CLAUDE.md` docs). `CLAUDE.md` and `AGENTS.md` files have a hard limit of 180 lines and 12,000 chars enforced by `no-mistakes`. When a doc is near its limit, move detailed content to a sub-document in the same directory and cross-link from the parent. When a feature also requires splitting a component or refactoring to stay within limits, include that refactor in the same feature commit — not a follow-up fixup.
- Reuse existing utilities, types, fixtures, patterns, and ownership boundaries before creating new ones. Search the relevant workspace and its docs first; add a new abstraction only when no existing owner cleanly fits.
- Keep changes scoped to the requested task and the nearest ownership boundary. Do not fold unrelated refactors, doc gaps, dependency upgrades, or latent bugs into the current PR.
- Keep PRs under 150 changed files so CodeRabbit can review them. If a coherent task would exceed that, first check whether it bundles **independent** work that belongs in its own worktree and PR targeting `main` (see [Git And PRs](git-and-prs.md)). If you create a temporary extra worktree for that split, put it under the OS tmpdir per [Start Of Work](start-of-work.md). Size alone is not a reason to stack. If the task is one source issue and genuinely atomic, ship it as one PR and note the >150-file review limitation in the PR body for human sign-off. Ask before filing child issues that would make a native stack possible.
- There is no such thing as a "pre-existing issue" for agent work. If you see an issue that blocks validation, affects your changes, or would make the PR misleading, fix it or resolve it. For out-of-scope problems, use GitHub issues to search for an existing issue or create a follow-up.
- Before treating a newly discovered blocker as part of the task, reproduce it against refreshed `origin/main`, then search for an existing fix or issue. If an existing fix resolves the blocker, use and retest it. Otherwise, whether or not an issue exists, ask the human whether to widen the accepted scope or only link or record a follow-up. Filing an issue records work but does not amend the accepted plan or authorize implementation.
- If an out-of-scope improvement is worth tracking, create a follow-up issue and include the URL in the PR description under `## Follow-ups`. Main agents should prefer delegating GitHub issue work to the `github-issue-agent` subagent whenever it is available. If the subagent is unavailable but `gh` is authenticated and a GitHub remote is present, read and follow the shared [github-issue](../github-issue/SKILL.md) policy directly, including duplicate search, live-label, milestone, and project classification, and post-create verification. If `gh` is unauthenticated or no GitHub remote is present, stop and request the missing setup. Before naming any repository as a cross-repository follow-up's home — however the deferral is worded ("this belongs in `owner/repo`", "follow up in `owner/repo`", a bare repository URL, etc.) — resolve that repository and require its returned canonical `nameWithOwner` to equal the name being written; for a URL-form deferral, extract the `owner/repo` path segment first (`https://github.com/owner/repo` → `owner/repo`, dropping any trailing `.git`, slash, or subpath) and compare that extracted identity, never the raw URL string, against the returned `nameWithOwner` — a renamed repository's redirect exits `0` under the stale name, so existence alone proves nothing. On a mismatch, write the canonical name; if the name does not resolve at all, do not defer to it — file the follow-up in this repository through the filing path above. Record the outcome (`matched`, `renamed from <stale name>`, or `unresolvable — filed in this repository`) in the PR description. This "file it here" disposition assumes the filing authority described above; a non-mutating context without that authority (for example, an Auto Harness automation prompt) instead records the follow-up as a recommendation scoped to the current repository and must state that narrower disposition explicitly.
- When editing one row of a status, compliance, or parity table, diff it against every sibling row. Reconcile any contradicting settlement or timeout convention between rows, or give one unified explanation in the PR description for why they legitimately differ.
- Update `docs/**` and the nearest workspace docs whenever you change behavior or learn something they should have captured — keeping `docs/**` current is what lets future sessions read docs instead of re-exploring the codebase. When you add a new `docs/**` page, add it to the [`docs/README.md`](../../../docs/README.md) index and the relevant catalog ([`docs/catalog/README.md`](../../../docs/catalog/README.md), [`backend/catalogs/README.md`](../../../backend/catalogs/README.md), or the workspace `README.md`). `CLAUDE.md` points at that catalog, not each page. An unindexed page is invisible to "read docs first." Keep cross-links bidirectional where repository docs require it: `docs/**` should link to relevant code entry points, and the nearest workspace `CLAUDE.md` should keep a one-line pointer to the catalog or owner page. Instruction placement is in [`docs/CLAUDE.md`](../../../docs/CLAUDE.md).
- Do not restate a value that another file owns — a config, workflow, constant, or schema. Point at
  it instead; a hedged value in prose (`currently 32MB`, `as of July 2026`) is a sign it belongs
  elsewhere. See [docs/CLAUDE.md](../../../docs/CLAUDE.md) for the full rule and its exceptions.
- When a doc describes a lifecycle, state machine, request path, queue pipeline, subsystem handoff, or decision flow, add or update a Mermaid diagram when it makes that behavior easier to verify. Keep diagrams source-of-truth and compact: prefer `flowchart` for pipelines, `sequenceDiagram` for request/actor handoffs, and `stateDiagram-v2` for status transitions. Do not add decorative diagrams that restate a table without reducing ambiguity.
- When adding or renaming a CI transient-retry rule, update `docs/development/ci.md` in the
  **same commit** — `ci/transient-retry/__tests__/doc-sync.test.mts` fails CI on drift. When adding
  or renaming an env var, update the env-var docs in the same commit. When adding or renaming a
  tool in `.mise.toml`, do not copy the exact version into markdown; point at `.mise.toml`. Dual
  executable pins (lychee and gitleaks in `.mise.toml` and workflow YAML) stay in lockstep via
  no-mistakes `version-pin-consistency`.
- Removing a timeout, deadline, or abort bound requires either a replacement bound on the same code path, or documented evidence that every caller already supplies its own bound plus a test exercising that path with a caller-supplied bound. State in the PR description which of the two forms applies.
- Do not leave dead code, unused exports, stale comments, or compatibility shims. For this unlaunched app, edit canonical schema creators and current producers/consumers together; do not add upgrade-only migration deployments or backfills. Preserve fresh-bootstrap integrity, external protocols, replay, and security controls. Before adding storage, classify JSON and identifier fields against [prelaunch relational storage](../../../docs/development/postgres-schema-rules.md#prelaunch-relational-storage); internal references need concrete FKs even when they are primary/unique keys or historical audit fields.
- Always increase relevant code coverage for changed behavior and never decrease it. Aim for **100% patch coverage** of new/changed code, even when uncovered code predates the task. Not decreasing overall/project coverage is an aspiration, not something CI enforces — CI checks only patch coverage on changed lines and has no historical baseline (see [Coverage Gates](../../../docs/development/reference-ci-coverage-gates.md)). Verify locally with `pnpm run coverage:patch:affected` (fast, advisory-by-default pre-check; pass `--strict` to block) or `pnpm run coverage:patch:full` (slower, reproduces the exact merged CI gate).
- For new features, API endpoints, service functions, and user-facing workflows, add focused tests. Follow workspace test rules in the relevant `CLAUDE.md`.
- For regression work, prove an existing focused test fails before the fix or add a focused test that would have caught it; do not add a duplicate when the existing boundary already owns the contract. Apply the [Test Value and Safe Reduction](../../../docs/development/reference-tests-value-and-reduction.md) gate.
- For every regression or code issue discovered in CI, add a test that fails before the fix and passes after it.
- Verify before reporting completion: exercise the changed behavior through its real boundary, observe the result, and report each automated, live, and blocked validation surface independently. Do not infer success from static inspection alone when end-to-end verification is feasible.
- Never mock PostgreSQL, Valkey, queues, workers, or internal service calls. Do not add mocks because setup is inconvenient; use real integration tests with existing fixtures and assert persisted state, queued jobs, emitted messages, or processor effects.
- Mock only external APIs such as OpenAI, Stripe, OAuth, S3, Cloudflare Turnstile, or HTTP crawlers, and keep `vi.mock()` / `vi.spyOn()` usage in `.mock.test.<ext>` files. External provider calls that need mocking belong behind tagged `@modules/*` integration exports.
- Avoid partial internal mocks and mock-only helper barrels because they drift when imports change and can hide missing exports.
- **Test-first**: write `it('description', () => { /* TODO */ })` stubs for all planned test cases before writing implementation code when new coverage is needed. Use the [Test Value and Safe Reduction](../../../docs/development/reference-tests-value-and-reduction.md) gate to avoid forcing duplicate tests for an already-owned contract.
- **Mock factories over inline stubs**: use named factory functions (`function makeMockTopic(overrides?: Partial<Topic>): Topic`) instead of hard-coded `vi.fn()` stubs inline. Factories are reusable across `describe` blocks and make overrides explicit.
- **Stubs and placeholders are authoring scaffolding, not deliverables**: the `/* TODO */` test stubs above are transient — replace their bodies with real assertions before you report completion (see "Verify before reporting completion" above). Mock factories and other test doubles are legitimate, permanent test infrastructure, not placeholders — they stay. Delivered code and tests must contain no placeholder or fake data, no stubbed or hardcoded returns posing as logic, and no `TODO`-as-final. This is how the root **No stubs or placeholders** principle coexists with the test-first workflow.
- **After modifying a hook or function signature**, run `rg 'hookName\|mockName' --type ts` to find all call sites and mock usages that need updating before compiling or pushing.
- For frontend changes, follow the independent live-browser and screenshot-credential preflights in [Start Of Work](start-of-work.md), inspect the rendered result with the supported interactive browser recorded in the plan, and capture at least one representative screenshot when the upload-credential preflight succeeds. Attach it to the PR with `pnpm run pr:attach-screenshots ...` following <https://github.com/jonathanong/gh-pr-attach-screenshots>. Do not commit screenshot artifacts or Playwright snapshot image files. Missing upload credentials block attachment only, while a missing interactive browser blocks live visual QA even when automated browser tests pass.
- If a browser recorded as `available` becomes unusable during implementation, troubleshoot it with the supported browser workflow. If it remains unavailable, record the concrete `exception` reason on the accepted Plan issue and obtain renewed human acceptance before omitting live visual QA.
- If credential preflight fails, continue local visual QA but skip capture performed solely for PR upload. Report `Visual verification: passed locally (<flow or artifact>).` only when visual verification actually passed, followed by `Screenshot attachment: blocked by the upload-credential preflight: <exact CLI diagnostic>; no screenshot was attached.` If attachment later fails because of repository access or SAML authorization, retain the visual-verification line and report `Screenshot attachment: blocked during upload: <exact CLI diagnostic>; no screenshot was attached.`
- Keep validation reporting independent: use `Visual verification: <result>.`, `Automated browser tests: <result>.`, and `Screenshot attachment: <result>.` as separate lines, and never substitute one result for another.

## Static-Analysis Reminders

- `vi.mock()` / `vi.spyOn()` are allowed only in `.mock.test.<ext>` files. Regular `.test.<ext>` files must not use them.
- Vitest tests must keep `it`/`test` cases and hooks inside a top-level `describe(...)` block, and every `vi.fn` call must include an explicit function type parameter such as `vi.fn<() => unknown>()` or a narrower project type.
- `@data-stores/psql` imports belong in services, except for explicit route/system allowlists.
- `.roles` access belongs in `backend/services/`; routes and systems should call service functions that perform authorization checks internally.
- `index.mts` files must be barrel exports or single-purpose files.
- `setTimeout` delays must be at most 5000 ms; do not use `setTimeout` in loops or consecutive `setTimeout` calls.
- Avoid banned wait primitives in Playwright: `page.waitForTimeout`, raw `page.goto` except response-capture cases, and `page.waitForLoadState('networkidle')` outside the allowed helper.
- `sanitize-html` and `markdown-it` are banned in TypeScript; use Rust NAPI equivalents.
- Package `overrides` are disallowed in `package.json`.
- Prefer `-` over `_` in filenames.
- Migration and SQL idempotent safety are enforced by `squawk`; final PostgreSQL schema conventions are enforced by `pnpm run test:backend:postgres-schema`.
- Keep tests idempotent on dirty databases: randomize IDs, slugs, usernames, and unique values; do not delete rows.
