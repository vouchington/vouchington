## Start Of Work

- At the start of a new interactive root Codex session without `CODEX_THREAD_ID`, establish its
  blackboard identity through the script procedure with `--root-codex --new-root-codex-session`
  exactly once. Later root-aware script calls pass only `--root-codex`; children and detached
  processes never pass either root flag. See [blackboard](../blackboard/SKILL.md).

- Always work from the repository root of the current worktree. If you are in a worktree, that worktree is the root for all commands.
- Scratch files go under `${TMPDIR:-/tmp}` (Node: `os.tmpdir()` / `mkdtemp`). Never hardcode `/tmp`.
- When the agent itself runs `git worktree add` for a throwaway or subagent checkout, create the directory under `${TMPDIR:-/tmp}` with `mktemp -d` or Node `os.tmpdir()` / `mkdtemp`. Never hardcode `/tmp`. Never put that checkout in the repository (including `.claude/worktrees`, `.codex/worktrees`, `.cursor/worktrees`, `.worktrees`) or under `~`, `~/worktrees`, or `../worktrees`. This rule does not apply to the current session worktree, human-owned trees, Auto Harness CI checkouts, or harness-owned isolation trees; do not move, recreate, or re-add Grok `isolation: worktree` checkouts under `~/.grok/worktrees` or Cursor Agents Window trees under `.cursor/worktrees`. If that throwaway tree was web-initialized, remove it with `./dev/teardown --yes --remove`; otherwise run `git worktree remove` from the main worktree or any directory outside the throwaway tree; if the directory is already gone, `git worktree prune`. This does not authorize extra worktrees: write agents stay serial in the current session worktree.
- Always work in a non-main worktree. Do not change the main worktree unless the user explicitly instructs you to do so, or you are running inside a GitHub Actions Codex workflow (scheduled prompts, fix-main, fix-issue, shepherd), where the workflow's fresh repository checkout is the workspace.
- At start of work, record the workspace setup state in notes or the PR body as `Workspace setup: ./dev/initialize monorepo`, `Workspace setup: ./dev/initialize backend`, `Workspace setup: ./dev/initialize web`, `Workspace setup: Auto Harness scheduled prompt`, `Workspace setup: Automation fix-main run`, or `Workspace setup: not needed, because ...`. Use `Workspace setup: Auto Harness scheduled prompt` only for Auto Harness scheduled prompt runs where the trusted workflow already prepared the fresh checkout, and `Workspace setup: Automation fix-main run` only for Fix Main automation runs where the trusted workflow already prepared the fresh checkout (see [fix-main.md](../../../docs/prompts/automation/fix-main.md)). Run `./dev/initialize monorepo` for lint-only, unit-test, or frontend screenshot work; run `./dev/initialize backend` for DB/Valkey-backed backend tests that don't need the full stack; run `./dev/initialize web` when the full local stack is needed. Unlike `Workspace setup:`, the sibling `Agent:`/`Device:`/`Worktree:` provenance lines are tool-injected by `dev/pr-description.mts create`/`update` — never author them by hand (see [git-and-prs.md](git-and-prs.md)).
- Before initializing the web stack for frontend screenshot work, run `./dev/initialize monorepo`, then run `pnpm run pr:attach-screenshots --check-upload-credentials` outside the sandbox. After the preflight completes, run `./dev/initialize web` and perform local visual QA; capture a screenshot for PR attachment only when the preflight succeeds. A failed credential preflight does not block local visual QA; follow the fallback and reporting rules in [Implementation](implementation.md).
- If `./dev/initialize web` is needed but blocked by Docker, PostgreSQL, or other local prerequisites, first retry with sandbox mode disabled when Docker or local auth may be running outside the sandbox. If it is still blocked, record that blocker in the PR notes and still run every relevant check that does not require the web stack.
- `pnpm run ...`, `pnpm exec ...`, `pnpm --dir ...`, `pnpm install ...`, and `pnpm test ...` have Claude OS-sandbox exclusions and Codex allow prefixes. A Codex allow runs the matched command outside the sandbox without a prompt. If a command still hits a sandbox denial (for example, a compound command without a matching allow), retry the exact command outside the sandbox when store writes or sockets are required. Codex reusable prefixes for those families are `["pnpm", "run"]`, `["pnpm", "exec"]`, and `["pnpm", "--dir"]`. If the unsandboxed retry is still blocked, record the blocker and continue independent checks. `pnpm --filter ...`, `pnpm dlx ...`, and `corepack pnpm ...` have no Claude exclusion or Codex allow and use the ordinary sandboxed path; a broad prefix would also unsandbox arbitrary registry execution. For a sandbox failure, prefer a narrow invocation such as `pnpm --dir <workspace> run <script>` over granting `["pnpm", "--filter"]`. The approved `npx pr-shepherd ...` / bare `pr-shepherd ...`, `npx vitest ...`, `npx oxlint ...`, `npx oxfmt ...`, and `npx no-mistakes ...` families likewise have Claude exclusions and Codex allows (e.g. `["npx", "vitest"]` or `["pr-shepherd"]`); no other `npx` family is pre-approved. The same holds for `node dev/pr-description.mts ...` and `node dev/plan-issue.mts ...` with `["node", "dev/pr-description.mts"]` and `["node", "dev/plan-issue.mts"]`, and bare `no-mistakes` with `["no-mistakes"]`. Grok and Cursor keep their process-wide workspace sandbox; Grok cannot relax it mid-session. Under workspace-write, run `pnpm exec` serially (pnpm 11 opens a shared SQLite store; no-mistakes holds a machine-wide lock). For parallelism of oxfmt/oxlint/vitest, invoke `node_modules/.bin/<tool>` instead of a second concurrent `pnpm exec`.
- `git` and `gh` authenticate with the host's own `gh` login (`~/.config/gh`) and SSH key (`~/.ssh`). That is the intended credential for every session, Auto Harness sessions included, which is why `git *` and `gh *` are excluded from the OS sandbox (see [Agent Sandbox](../../../docs/development/agent-sandbox.md)). The exclusion matches only a plain command, so a piped or chained call such as `gh pr list ... | head` still runs sandboxed and fails with `open ~/.config/gh/config.yml: operation not permitted`, `No GitHub token found`, or an SSH/proxy refusal. Prefer plain calls (use `--jq` instead of a pipe). When one of these denials still happens, retry the same command with sandbox mode disabled (Claude `dangerouslyDisableSandbox: true`; Codex `sandbox_permissions: "require_escalated"`) instead of stopping for missing credentials. Unset `GH_TOKEN`/`GITHUB_TOKEN` is expected and is not a blocker.
- If Codex `apply_patch` fails because the sandbox helper cannot initialize (for example `bwrap: setting up uid map: Permission denied` or `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`), use the narrowest escalated edit possible, immediately inspect `git diff`, run `pnpm exec oxfmt <changed files>` or `pnpm run oxfmt:check` as appropriate, and run focused validation. Avoid broad inline shell rewrites for shell-sensitive files such as JS/TS template literals, SQL dollar quotes, YAML heredocs, and shell scripts unless the replacement is mechanically verified. On a CI runner, the identical error is a host-provisioning failure, not something to work around locally, which `harness-dispatch.yml`'s preflight step now fails loudly on instead of silently degrading to comment-only (#8264).
- If working inside tmux (`$TMUX` is set), keep the current window name and pane title in sync with the work using `./dev/tmux-name <name>` (1–2 lowercase hyphenated words, for example `agent-workflow`). Always run `./dev/tmux-name <name>` with sandbox mode disabled so tmux targets the agent's `$TMUX_PANE` instead of another attached client window. Rename at three points:
  1. Once you understand the topic of the conversation (typically right after the first user message), pick a descriptive name and rename immediately.
  2. When a plan is accepted, refine the name if the accepted scope differs from the initial topic.
  3. When a PR is created, suffix the name with `-pr<number>`, for example `./dev/tmux-name agent-workflow-pr123` (see [Git And PRs](git-and-prs.md)).
- Before planning or changing code, search `docs/**` and read the relevant workspace `CLAUDE.md` files for prior art, constraints, utilities, and test rules. Cite the specific files reviewed in saved plans. For every file path mentioned in the source issue body, verify it still exists in `HEAD` (`ls <path>` or `fd` when the exact path may have changed) before building the plan — issue paths are point-in-time hints written when the issue was filed, not guarantees about the current codebase. Treat `docs/**` as the durable map of the codebase, not just reference material: if you had to explore because `docs/**` did not already answer the question, that is a documentation gap — before finishing, record what you learned (architecture, file locations, patterns, gotchas) in the relevant `docs/**` page (index it; see [`docs/CLAUDE.md`](../../../docs/CLAUDE.md)) so the next session reads docs instead of re-exploring.
- At session start, use the `./dev/check-fresh-base` context to classify the current branch against freshly fetched `origin/main`. A clean match can proceed. During Plan Mode, do not reset or rebase merely because the branch is behind, ahead, or diverged: for a new task, treat `origin/main` as the source of truth and inspect its files with `git diff` or `git show`; for resumed work, preserve the branch and account for upstream changes in the plan. If the working tree is dirty, the fetch failed, or it is unclear whether the task is new or resumed, ask before choosing a destructive or history-changing action. Never infer permission to pass `--force`. See [Fresh-base planning](../../../docs/development/README.md#fresh-base-planning).
- **Reconcile open PRs and stacks before starting anything new.** At start of work, and again before opening any PR or `gh stack init`, run the unfiltered ledger query — `gh api repos/{o}/{r}/stacks --jq '[.[] | select(.open)]'` and `gh pr list --state open --limit 100 --json number,title,author,body` — regardless of who created them. Surface any open stack or unfinished layer before creating more, then partition the result by ownership (an `Agent: ... session <id>` line matching this session's `resolveSessionId()`, or a PR the human named in this session). This must be unfiltered by session: the failure it guards against is an agent forgetting a stack it (or another session) made and starting a rival one, which is exactly the case a session-scoped query would miss in a brand-new or post-compaction session. See [stacked-prs](../stacked-prs/SKILL.md#keep-track-derive-the-ledger-never-remember-it) for the full procedure and the per-PR ownership check.
- For in-scope implementation work, load the [planning skill](../planning/SKILL.md) before writing the plan. It owns the premise challenge, exact Plan schema, impact and test evidence, independent planning review, and mandatory validated Plan issue. Keep the plan proportional to the work.
- During planning and before implementation, follow the planning skill's exact [live-browser preflight](../planning/references/live-browser-preflight.md).

- A plan is accepted when a human approves it, a follow-up implementation adopts it, or planning exits plan mode. If the accepted plan changes, comment on the Plan issue with what changed and why before continuing.
- When starting implementation from an accepted plan, fetch and compare against the latest `origin/main` again because code may have merged during planning. For a new task planned from `origin/main` while the worktree was stale, run unforced `./dev/reset-worktree`, then re-read the relevant sources before editing. For resumed unstacked work, inspect `git diff --name-only origin/main...HEAD`, preserve the branch, and run `git rebase origin/main`. For a resumed native stack, first re-derive topology from `gh api repos/{o}/{r}/stacks/<n>` rather than trusting local `gh-stack` metadata — a stale local base ref after a remote relink or rebase can replay already-landed commits (formerly filed as jonathanong/filaments#11426) — then use `gh stack rebase` or `gh stack sync`; do not check out `main`. If local changes or ambiguous task intent make either action unsafe, ask first. Follow the conflict-resolution rules in [Git And PRs](git-and-prs.md).
- When a task closes an issue that carries a GitHub milestone or belongs to an org project, expect `node dev/pr-description.mts validate <pr>` to audit that milestone's or project's other open issues once few enough remain — see the issue-supersession, milestone-completion, and project-completion audits in [Git And PRs](git-and-prs.md).
- The main agent is the orchestrator: it owns user intent, planning, task boundaries, delegation, integration, and final validation. The [planning skill](../planning/SKILL.md) owns subagent selection and progressive-disclosure impact and test discovery.
- Keep unbounded tool output out of the main session. Do not ingest raw `gh api --paginate` result sets, `gh run view --log-failed` streams, CI log archives, or session transcripts inline. Write the payload to a temp file and read a filtered summary, or delegate the read to a subagent that returns a short verdict. Remove the temp file after reading. For GitHub Actions logs, dispatch a subagent that follows [review-ci-logs](../review-ci-logs/SKILL.md) and returns a short verdict; do not run the archive inspection in this session. For the routine post-push fix-and-resolve tail, dispatch a subagent per [Implementation](implementation.md) and [Git And PRs](git-and-prs.md); keep only the verdict in this session.
- Outside planning, use `rg` for text search, `fd` for path discovery, and `pnpm exec ast-grep` only when structural matching is needed.
- If `no-mistakes` or `pr-shepherd` surface a bug or missing feature during work, route it through the `github-issue-agent` subagent rather than working around it silently. The [github-issue skill](../github-issue/SKILL.md) files directly in an authorized owning repository; when that repository is not authorized, it files a Vouchington tracking issue with the `dependencies` label and a copy-paste-ready external report.
- Live runtime permission overrides take precedence over custom-agent sandbox settings. Do not dispatch a read-only role from a run where its no-mutation boundary cannot be mechanically enforced.
