# Referral Links

Referral links allow users to share affiliate/referral URLs on referral program topics and on any other topics linked to a referral program via `topics.referral_program_id`. Links are displayed in a prioritized order based on the viewer's relationship with each link owner.

## Ranking and caching

Why two reads: the part of the list that depends on the viewer is small and cheap, and the part that is the same for everyone is expensive, so only the second is cached.

- Official Voucha links rank after the viewer's network groups and before everyone else, so a trusted person's link is never pushed below ours, while ours stays visible even when the viewer has a full network. They are always included and do not count toward the personalized link limit. The same order holds in "show all", whose `priority_group` is 5 for official links and 6 for every other link, so 5 only ever means official; clients must not infer rank from the number beyond the order and the `is_official` badge.
- A request chooses its own `limit` (at least 1, default `personalized_link_limit` = 5, at most `personalized_link_max_limit` = 25, both in `prioritized-referral-links-work-config`; 25 is also the hard ceiling of both). REST and the MCP `get_referral_links` tool treat it the same: a non-positive or non-integer `limit` is rejected (400 on REST, an invalid-limit error on MCP) and a larger one is clamped to the maximum. Official links are extra and do not count toward it. The same limit caps the page and every in-network subquery, so the reads cannot disagree. The web aside sends no limit and shows the default as returned.
- Each in-network group (mutual follow, follow, referred you, rated positively) is its own subquery. It applies every link check (program, active, not yourself, not the official account, not muted or blocked, child visibility) before its limit, so people without a usable link never use up a slot, and a full follow group cannot hide a mutual follow. A group keeps the people with the newest activated link (`activated_at DESC, id`), so a strong contributor outside the newest few is not considered. A person in several groups keeps the best one. Ranking by contributions, reviews and membership tier then runs only over the people the groups return, at most four times the limit.
- In-network links (mutual follow, follow, referred you, rated positively) come from one statement for signed-in viewers, capped at the requested limit (one page: it ignores `after` and returns no next page). Rated positively looks only at votes on posts newer than `voted_post_max_age_days` in `prioritized-referral-links-work-config` (default 90, maximum 365 because read cost grows with the window), and at most the latest 1,000 of them. A vote cast today on a post older than the window no longer counts toward ranking; the post id bound is what lets PostgreSQL prune the vote partitions without a new index. The limit also caps mutual follows and each group, and a viewer with any in-network link gets no out-of-network fill.
- Out-of-network links (official links plus the shared ranked others) come from one statement per program with no viewer input, ranked once and sized to `personalized_link_max_limit`. It is cached in Valkey for five minutes and cleared when a program's links are added, activated, deactivated or removed; the cache key is the program, never `limit` or `after`. Each request removes the viewer's own link and their muted and blocked authors from the cached list, then applies `after` (the last link id of the previous page, located before that filter) and `limit`, so pages within one cached list share one ranking. The list is the top `personalized_link_max_limit` (25) links, so a page is only short when that list runs out; "Show all" lists the rest. A link write or a refresh re-ranks the list, so between two requests a link can repeat or be skipped, and a cursor whose link has left the list is refused (`Invalid cursor format` on REST, `Invalid cursor` on MCP, the shared mapping of the pagination decoder and the MCP cursor result); the client starts again from the first page. A lowered maximum applies at once because every request clamps to it; a raised maximum reaches the cached list when it next refreshes (within five minutes, or at the next link write). Deleting a parent link and re-unfurling it clear the programs of the child links they remove. Membership lapses, crawler deactivation, label edits and the membership-downgrade child cleanup are not cleared and wait out the TTL.
- A clear does not take effect at once. The first miss after a clear can read a lagging replica and cache the old list for five minutes, so a deleted link can stay visible for up to that long. No LSN or replica barrier is used; the five-minute TTL is the bound.
- Stale refresh is on for this cache: during the last tenth of the TTL a read returns the cached list and one background load per process replaces it. A link write deletes the key, so the next reads are real misses and are not coalesced; each loads the list.
- The backend filters the cached list per viewer (own link, muted, blocked). A viewer with any in-network links sees no personal out-of-network links; official links always come from the cache.
- "Show all" is not ranked: it pages newest first with a keyset on the link id.
- Queries compare the official account's id. The id is resolved from the account's username once per process.
