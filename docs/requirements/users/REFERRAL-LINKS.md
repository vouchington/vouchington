# Referral Links

Referral links allow users to share affiliate/referral URLs on referral program topics and on any other topics linked to a referral program via `topics.referral_program_id`. Links are displayed in a prioritized order based on the viewer's relationship with each link owner.

## Ranking and caching

Why two reads: the part of the list that depends on the viewer is small and cheap, and the part that is the same for everyone is expensive, so only the second is cached.

- The personalized link limit is `personalized_link_limit` in `prioritized-referral-links-work-config` (default 5, maximum 25, the size the cached list was before this limit existed). Official links are extra. Every ranking subquery uses the same value, so the in-network read, the out-of-network list and the per-viewer slice cannot disagree. The web aside shows the list as returned.
- Each in-network group (mutual follow, follow, referred you, rated positively) is its own subquery. It applies every link check (program, active, not yourself, not the official account, not muted or blocked, child visibility) before its limit, so people without a usable link never use up a slot, and a full follow group cannot hide a mutual follow. A group keeps the people with the newest activated link (`activated_at DESC, id`), so a strong contributor outside the newest few is not considered. A person in several groups keeps the best one. Ranking by contributions, reviews and membership tier then runs only over the people the groups return, at most four times the limit.
- In-network links (mutual follow, follow, referred you, rated positively) come from one statement for signed-in viewers, capped at the personalized link limit. Rated positively looks only at votes on posts newer than `voted_post_max_age_days` in `prioritized-referral-links-work-config` (default 90, maximum 365 because read cost grows with the window), and at most the latest 1,000 of them. A vote cast today on a post older than the window no longer counts toward ranking; the post id bound is what lets PostgreSQL prune the vote partitions without a new index. The limit also caps mutual follows, and a viewer with any in-network link gets no out-of-network fill.
- Out-of-network links (official links plus the top ranked others, up to the limit) come from one statement per program with no viewer input. It is cached in Valkey for five minutes and cleared when a program's links are added, activated, deactivated or removed. The limit is not part of the cache key: lowering it applies at once because the per-viewer slice reads it, and raising it reaches the cached list within the five-minute TTL. Because the cached list holds only the limit, a viewer whose own link or a muted or blocked author ranks in it sees fewer than the limit. Membership lapses, crawler deactivation, label edits and child soft-deletes are not cleared and wait out the TTL.
- The backend filters the cached list per viewer (own link, muted, blocked). A viewer with any in-network links sees no personal out-of-network links; official links always come from the cache.
- "Show all" is not ranked: it pages newest first with a keyset on the link id.
- Queries compare the official account's id. The id is resolved from the account's username once per process.
