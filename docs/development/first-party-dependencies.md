# First-Party Dependencies

These packages are authored and maintained by Jonathan Ong. When you encounter friction, gaps, or bugs with them, give feedback: capture it in session retrospectives (`/retrospective`) or use the `github-issue-agent` agent instead of silently working around it locally. File directly in an authorized owning repository; otherwise file a Vouchington tracking issue labeled `dependencies` with a copy-paste-ready external report.

The authoritative registry is `pnpm-release-age-policy.permanentPackages` in [`.no-mistakes.yml`](../../.no-mistakes.yml). Registry membership requires an audited default-branch npm trusted-publishing (OIDC) workflow. Keep both in sync: add entries to that configuration and this table together when a new first-party package is added.

The [scheduled first-party dependency audit](../prompts/scheduled/first-party-dependencies.md)
rechecks this registry and local workarounds against current upstream releases, then tracks one
confirmed root cause per run without changing dependencies or code. The
[scheduled upstream adoption prompt](../prompts/scheduled/upstream-adoption.md) removes one local
workaround or copied package feature per run once the upstream fix or capability is released.

First-party packages follow the same version rule as every other external dependency: a caret range
and one version across all workspaces, enforced by Syncpack (see the
[docs pinning policy](dependency-updates.md#docs-pinning-policy)).

Extraction boundary: generic algorithms live in the platform packages; the local `@modules/*`,
`@services/*`, and `@ts-shared/*` wrappers keep Voucha import paths, product policy, runtime
configuration, HTTP error contracts, orchestration (AWS clients, API egress-proxy routing, GlideMQ
manifests, session mint/cookies, ActivityPub signature policy), SQL and transactions, and
authorization. Isomorphic primitives belong in `@vouchington/utils`; Node-only helpers do not.
`@modules/token-secrets` delegates key parsing and AES-GCM to the package and must not remap kids
or accept noncanonical ciphertext.

`glide-mq`, `@glidemq/dashboard`, and `@glidemq/speedkey` are heavily-used vendored dependencies authored by [avifenesh](https://github.com/avifenesh). They are not first-party, but are bundled with a skill and tracked closely.

## Screenshot Upload Credentials

Before frontend browser QA that will produce a PR attachment, follow the [agent workflow credential preflight](../../.agents/skills/agent-workflow/start-of-work.md). `gh-pr-attach-screenshots` prefers a `GH_SESSION_TOKEN`; supported-browser discovery of the `user_session` cookie is the fallback. The session token grants full account access: never put it in command arguments, logs, documentation, commits, or PR content. Ordinary `GH_TOKEN` and GitHub CLI PAT credentials cannot upload GitHub-hosted images.

`pnpm run pr:attach-screenshots --check-upload-credentials` checks only whether upload credentials are available and accepted. The root package script keeps the CLI dependency visible to Knip. The check does not prove repository write access or organization SAML authorization; the final attachment command validates those separately. Do not insert a pnpm `--` separator: pnpm forwards `--` to `gh-pr-attach-screenshots`, where it is rejected as an attachment argument.
