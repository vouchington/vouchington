# Agent Session Hooks

[Back to Dev Environment Reference](README.md#agent-session-hooks)

Every hook entrypoint reads its stdin payload through `dev/codex-hooks/hook-payload.mts`
(`readHookPayload`, `extractToolCommand`, and the tool-name, session-id, file-path, and runtime
helpers). That module has no policy imports, so non-policy hooks never load the PreToolUse policy.
`readHookPayload` also maps Cursor's Claude-compat dialect to Claude's through
`dev/codex-hooks/cursor-payload.mts`: tool `Shell` becomes `Bash`, and its `tool_output` JSON
string `{exitCode, output}` becomes `tool_response` `{exit_code, stdout}`.
Cursor and Grok run the `.claude/settings.json` hooks below through Claude-compat.

- **`./dev/check-fresh-base`** — SessionStart hook (Claude Code + Codex): fetches `origin/main`, then reports the branch name, clean/dirty state, and whether HEAD is ahead, behind, or diverged. A clean matching branch exits silently. Missing refs and fetch failures report that freshness is unknown instead of silently trusting cached state. Its guidance distinguishes new work from resumed work and never infers `--force`; the reset-or-rebase decision is made after Plan Mode. Set `CHECK_FRESH_BASE_SKIP_FETCH=1` to skip the network fetch (used by tests). Outputs raw JSON (hook format) when run manually. See [Fresh-base planning](../README.md#fresh-base-planning).
- **`./dev/check-web-init`** — SessionStart hook (Claude Code + Codex): nudges `./dev/initialize web` when `.initialized` is absent or not `"web"` from the worktree root, reminding the agent to run `./dev/initialize web` then `./dev/tmux` before UI/browser work. Exits silently when `.initialized` = `"web"`, on `compact` restart, or outside a git repo.
- **`node dev/codex-hooks/persist-session-id.mts claude`** — SessionStart hook (Grok and Cursor
  Claude-compat only): no-ops unless the runtime resolves to `grok` or `cursor`, then persists
  `.local/grok-session-id` or `.local/cursor-session-id` from the real hook id, or generates
  `<agent>-` + UUID when neither a payload id nor a valid persist file exists. Silent stdout. See
  [agent-harness-parity.md](../agent-harness-parity.md).
- **`node dev/check-blackboard.mts`** — SessionStart hook (Claude Code + Codex): prints `Blackboard sessionId: <id>` from the hook payload (every `vouchington-tooling` journal tool takes an explicit `sessionId`), then probes the hosted agent-blackboard deployment with `sessions list --limit 1` — a single bounded page that verifies the server, DynamoDB, and token in one round trip without draining the full sessions table. The session id is re-printed on a `compact` restart and under `CHECK_BLACKBOARD_SKIP=1`, which skip only the probe; the hook exits silently outside a repository, or when the payload has no id and the probe succeeds. On failure, emits an advisory availability note asking the user to verify `AGENT_BLACKBOARD_URL`/`AGENT_BLACKBOARD_TOKEN` and naming the CLI fallback, which an agent announces to the user. The note does not by itself stop the session. Set `CHECK_BLACKBOARD_SKIP=1` to skip the probe (used by tests). Inside the Claude Code sandbox (`SANDBOX_RUNTIME` set), it instead emits a "probe skipped, not an outage" context note — the sandbox denies `AGENT_BLACKBOARD_TOKEN` and blocks egress, so a sandboxed run can't distinguish a real outage from a withheld credential. The hook cannot see whether a harness connected the machine-registered server. See [agent-blackboard](../agent-blackboard.md#sessionstart-availability-check).
- **`node dev/codex-hooks/pre-tool-use.mts <claude|codex>`** — PreToolUse policy hook (Claude Code, Codex, Grok, and Cursor through Claude-compat). A block exits 2 with its reason on stderr and writes a runtime-compatible deny payload to stdout. It is a guardrail, not a security boundary; see the [hook threat model](../agent-sandbox.md#hook-threat-model). Session `hookCwd` (`tool_input.cwd` / `workdir`, payload `cwd` / `workspaceRoot`, else `process.cwd()`) is the base working directory. Sequential command-local `cd` on the inspected command, then the invocation's own `env -C` / `--chdir` wrappers, is the per-invocation cwd for relative `--body-file` and `gh-merge-base`. A `cd` run through a non-builtin wrapper (`env cd`, `nohup cd`) changes nothing, and an unresolvable `env -C` target leaves the cwd unknown; an explicit `--base` / `-B` (and `gh stack init --base` / `-b`) is still checked then, and only the checks that read the checkout are skipped: the `gh-merge-base` fallback and `gh stack init`'s HEAD-ancestry guard. See #10897. The entrypoint also injects the session checkout's home GitHub owners (`sessionHomeOwners` in `policy/github-checkout-owners.mts`, read lazily from `git remote -v`, `gh repo set-default`, and the root `package.json` `repository`, so a fork-only checkout still counts its declared upstream), so the PR and issue content rules skip a command that provably targets a repository outside them; merge authority and the `gh stack` policy never read it. Without a literal `--repo`, gh's own prefix may only set or unset variables (`VAR=x`, `env`, `env -u`; not `env -i`, `env -C`, or another wrapper), and the inherited `GH_REPO` and cwd remotes count as proof only for a top-level gh reached through nothing but `&&`-joined literal `cd`s with no `GIT_*` prefix. A nested `bash -c`, heredoc, or `$(…)` body, or any other command or joiner before gh (a short-circuited or pipelined `cd`, `builtin`/`eval`/function `cd`, `pushd`, a same-command `git remote set-url` or `gh repo set-default`), needs a literal `--repo` or `GH_REPO` prefix. Those home owners and cwd remotes come from mutable checkout state that the protected-hook-paths guard doesn't cover. That is accepted, because the content rules are conventions, not a security boundary, and the merge rules never read them. See #434.
- **`node dev/codex-hooks/post-tool-use-command.mts <claude|codex>`** — the single merged PostToolUse hook (Claude Code, Codex, and the Grok/Cursor Claude-compat runtimes), registered once on the `ExitPlanMode|Bash|run_terminal_command`/`ExitPlanMode|Bash` matcher group. It replaces what used to be three separately-spawned Codex hook processes (four on Claude Code) firing on the same tool call — Codex's single shell tool always serializes as `tool_name: "Bash"`, and `is_exact_matcher()` treats that matcher as exact alternation, so it matched ~77% of Codex tool calls. The entrypoint reads stdin and parses the hook payload exactly once, then runs the tmux checkpoint reminder in-process (`dev/tmux-reminder-post-tool.mts`'s `renderPostToolReminder`, ported from `tmux-agent-reminder`'s old `post-tool` case — see that script's own comment, including `VOUCHA_TMUX_BIN`) behind its own try/catch. The reminder writes stdout at most once, at the very end, so a partial or doubled hook response is impossible. Fail-open throughout: any error anywhere in the chain is swallowed and the process always exits 0. No hook records session evidence or appends Blackboard journal entries: agents write their own, following the [`blackboard` skill](../../../.agents/skills/blackboard/SKILL.md) (see [agent-blackboard](../agent-blackboard.md#agent-written-journal-entries)). Sandbox escalations and failures reach the retrospective's `## Sandbox & Permission Audit` through those journal entries, in the skill's block grammar.

Codex hooks consume their explicit payload `session_id` directly and never write the root-only
`.local/codex-session-id`: hook metadata cannot distinguish an interactive root from a spawned
Codex child. The interactive root CLI uses `--root-codex` and, once for an absent-thread new
session, `--new-root-codex-session`; children never use either flag.
