# Linters and Static Analysis

`pnpm run lint` fans out to: `oxlint`, `ast-grep`, `jscpd`, `oxfmt`, `selene`, `no-mistakes`, `repo-file-policy`, and `typecheck`.
On a stacked branch, run `pnpm run jscpd --base <parent-branch>` so the duplication ratchet
compares against the parent rather than `origin/main`; `lint` uses the `origin/main` default.

`repo-file-policy` also validates the shared lifecycle scenario schema, exact family consumer policy,
claims, canonical adapter dispatch, and executable evidence. Run the focused regression with
`pnpm exec vitest run --project static-analysis-tools static-code-analysis/repo-file-policy/lifecycle-scenario-contract.test.mts`
.

Swift/.NET source, local-LLM endpoint-policy, and native guard validation are owned by
[`vouchington/vouchington-clients`](https://github.com/vouchington/vouchington-clients); Vouchington
retains only the shared producer contracts those clients consume.

`no-mistakes` owns TypeScript compiler-gate coverage, including static local reusable workflows,
and the file-universe check (`tsconfig-file-coverage`) that every tracked TypeScript file belongs
to a compiler program.

`no-mistakes/no-inline-noop-promise-catch` is enforced for production `backend/**` and `web/**` in
[`.oxlintrc.json`](../../.oxlintrc.json), excluding the four configured test/test-helper path forms.
The 2026-09-10 inventory found 116 diagnostics in 70 production files (41 backend, 75 web), all
remediated through #11567 and #11568 after #11566 established the installed-rule consumer fixture
and configuration contract. The [static-analysis rollout guide](../../static-code-analysis/README.md#rolling-out-a-repo-wide-guard)

`shellcheck` is bash-oriented and does not flag zsh reserved-variable shadowing of `status` and
`pipestatus`; see [dev/CLAUDE.md](../../dev/CLAUDE.md).

`backend/tsconfig.json` sets `"lib": ["es2025"]` — no DOM. A type-only import of anything reaching
`vitest/config` (which re-exports `@types/jsdom`, carrying `/// <reference lib="dom" />`) pulls
`lib.dom` into the backend program transitively, and `@types/node`'s web-globals layer then defers
every web global (`fetch`, `Response`, `ReadableStream`, `setTimeout`'s overloads, …) to the DOM
types instead of Node's — silently changing what `typecheck:backend` accepts. Do not import
`vitest/config` (or a module that imports it) from `backend/**`.
`backend/types/lib-dom-absent.mts` is a type-only compile-time guard: if `lib.dom` re-enters the
backend program, `typecheck:backend` fails a `TS2344` naming the cause and pointing at
`tsc --explainFiles --project backend/tsconfig.json` to trace the edge.
`test-helpers/tsconfig.json` extends `backend/tsconfig.json` but legitimately loads `vitest/config`
itself (it is Vitest's own config layer) — its `lib.dom` count staying nonzero is expected, not a
regression to "fix" by chasing this guard into `test-helpers/`.

`config-path-references` (and the other presets sharing its tracked-only universe, e.g.
`package-json-workspace-coverage`) resolves every configured reference against `git ls-files`, not
the working tree, so a target that exists on disk but has not been `git add`-staged is invisible to
it. Running `no-mistakes` before staging a newly added config target fails with ``config path
`<reference>` from `<key>` does not exist``, which reads like a typo in the reference rather than a
staging gap. The remedy is `git add <file>` (index only, no commit needed) before rerunning — not
renaming or re-pathing the reference, and not chasing it as a bug in whichever rule reported it.
Keep troubleshooting notes about this version-agnostic: the message text is stable across releases,
so a hardcoded version number here would just be the next thing to drift.

Dev PostgreSQL helper changes should include `dev-tools` coverage for `dev/lib/db-target.sh`, dynamic `PGPORT` preservation in generated local `DATABASE_URL` values, and operation-specific non-local opt-ins before any schema-writing or destructive command runs.
