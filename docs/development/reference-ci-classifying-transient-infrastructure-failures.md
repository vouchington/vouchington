# Classifying Transient Infrastructure Failures

## Historical native CI fingerprints

The native workflow names and commands in the historical fingerprints describe the pre-extraction
Filaments CI topology. Current native CI and reproductions are owned by
[`vouchington/vouchington-clients`](https://github.com/vouchington/vouchington-clients); the
Vouchington retry policy below remains current.

[Back to CI Reference](ci.md#classifying-transient-infrastructure-failures)

Before rerunning a failed CI job, confirm the failure matches a known infrastructure signature
**and** that the latest runs on the target branch are green. A look-alike failure that matches
your diff is a real bug — do not rerun it. On non-`main`, non-Dependabot PR branches, once you
have confirmed the run matches a known-transient fingerprint, use
`node ci/transient-retry/rerun-known-transient.mts <run-id>` instead of manually matching rules
and calling `gh run rerun`.

Automatic `main` recovery runs only while `HARNESS_DISPATCH_ENABLED` and
`HARNESS_FIX_MAIN_ENABLED` are both exactly `true`. When either is unset, `fix-main.yml` does not
classify failures, rerun workflows, request fresh plans, reap locks, or dispatch Harness. The manual
PR-branch helper above remains available independently.

Every rerun rule has its own `maxAttempts` budget. Prior attempts are replayed chronologically,
and only a rule that wins ordered evaluation with a rerun decision increments its counter, so
unrelated failures do not consume the budget even when they created jobs. `ignore` decisions retain
shared attempt accounting. If evidence requested by a later
matcher is unavailable, reconstruction retains the proven ordered-rule prefix and omits the
failing rule and suffix, which use the conservative shared attempt count that discounts only
prior zero-job attempts. If the first rule's evidence is unavailable, every rule uses that fallback.

Bare job-timeout kills on `Static` `static-code-analysis / no-mistakes` have no auto-rerun rule. Hosted runners isolate separate
jobs, but a timeout within one job gives no evidence that distinguishes an infrastructure
stall from a real code-bug deadlock. The
[timeout forward guard](../../ci/transient-retry/no-mistakes-job-timeout-ceiling-inconclusive.test.mts)
derives each current timeout from its owning workflow and requires these ambiguous signatures to
dispatch for investigation instead of automatically rerunning.

The `cloudflare-worker-tsc-runtime-unknown-caller-pc` rule retries a TypeScript-Go
unknown-caller-pc crash only in the `static-code-analysis` job of
[Static Code Analysis](../../.github/workflows/static-code-analysis.yml). The area
`static-cloudflare` smoke check is not this fingerprint.

Cancelled idempotent workflows, including standalone `Static Code Analysis` runs, with no failed-job
signal are ignored instead of dispatching Codex. Unclassified timeouts are never blind-rerun.
Each path-scoped `main-*` workflow publishes its artifact unit after queue validation, then
dispatches the matching private-infrastructure receiver. Vouchington does not migrate databases,
mutate providers, or deploy runtime artifacts. The receiver remains disabled during the cutover.
After explicit Harness activation, `fix-main` auto-reruns catalogued transient failures on
individual Vouchington workflows; until then this path remains disabled. Deployment recovery belongs
to the private infrastructure repository.

The standalone Gitleaks workflow handles GitHub Release transport errors and retryable HTTP
responses in the job on pull requests: both the archive and checksum
download use up to three curl retries before the checksum is verified. Each attempt is capped at 15
seconds, and retries may start only inside a 35-second window, so each download is bounded at 50
seconds and both sequential downloads fit within the two-minute install step. The
`gitleaks-install-releases-download-flake` classifier remains available for diagnosis after those
in-job retries are exhausted; this workflow does not run on main pushes or subscribe to Fix Main.

The `static-web`/`build-web-targets` shared `expensive-build` host-lock watchdog and
acquisition-timeout rules retired with the self-hosted runner fleet: GitHub-hosted runners are
ephemeral and single-job-per-VM, so those shared-host lock races can no longer occur. The
`runner-shutdown-leaf-rerun` rule remains live for a clean cancellation of an idempotent leaf job:
its shared `runnerShutdownLeafRerunMatch` predicate requires complete logs and rejects OOM,
application, setup, and non-SIGTERM failure evidence before rerunning up to twice. This is distinct from
an unexplained non-143 exit code, which remains a real failure requiring investigation rather than
an automatic runner-shutdown rerun.

Credentialed-provider classification keeps each provider's specific evidence boundary. AWS accepts
only a bare Vitest timeout or the known SDK abort/timeout markers. Bedrock additionally requires its
500/runtime-host markers. OpenAI 429s require both the provider message and `rate_limit_exceeded`;
the provider-side 500 case requires every failing OpenAI block to contain the 500 message and
`OpenAI.makeStatusError`. OpenRouter accepts only the structured-decision client's HTTP 429/5xx
outcome or a failed response carrying both `server_error` and
`Flex processing is temporarily unavailable`. Assertion, validation, authentication, parser/schema,
mixed-project, and non-test terminal failures remain look-alikes that must be investigated. Project
ownership comes from each Vitest project's configured include glob rather than a hand-maintained
test-title list.

**Explicit OOM disqualifier:** `runner-shutdown-leaf-rerun` and its shared
`runnerShutdownLeafRerunMatch` predicate disqualify a sibling leaf job from counting as a clean
runner shutdown when any
fetched unsuccessful-job log contains either `Out of memory: Killed process <pid>` or a positive
`oom_kill` counter in its `== cgroup memory ==` diagnostics section. The rule and predicate require
every unsuccessful-job log to be available before treating a sibling as a clean shutdown, so missing
evidence cannot pass through a downstream-job bypass. The
Storybook watchdog row
does the same only for its runner-shutdown/operation-cancelled variant; its process-exit watchdog
and other bootstrap fingerprints are unchanged. The original failed-job log retains the killed
PID/RSS and cgroup evidence, so this does not add a classifier output schema.

The Storybook browser runner owns one monotonic 300-second session budget across at most three
whole-process attempts. Vitest's browser connection timeout and the runner's pre-test hang
threshold both use
`STORYBOOK_BROWSER_HANG_MS` (120 seconds by default), preventing the inner handshake timeout from
ending an attempt before the outer watchdog's promised startup window. Attempt 1 uses the
persistent Vite cache `.cache/vite/storybook-browser` unless
`STORYBOOK_BROWSER_PERSISTENT_CACHE=0` disables it or
`STORYBOOK_BROWSER_PERSISTENT_CACHE_DIR` overrides the directory. Optimizer stalls, add-on
runner-context races, virtual-module fetch failures, silent pre-test watchdog hangs, and pre-test
browser-session timeouts may recycle Vitest and Chromium before the shared deadline. Pure
browser/session failures preserve the ready Vite cache; optimizer, module-fetch, and missing-runner
evidence rotate it. The
`vitest-storybook-progress-reporter` emits bounded, monotonic `module-collected`, `module-start`,
and `module-end` markers; after the first marker, only an explicit localhost dynamic-module fetch
failure or add-on setup-file `Vitest failed to find the runner` before `|web-storybook-browser`
output remains retryable. A later no-progress interval or assertion failure is terminal. Bootstrap diagnostics record honest provider, page,
navigation, and orchestrator-WebSocket milestones; they do not refresh the watchdog. Verbose
browser-API and request-failure output is filtered or capped, retry diagnostics add bounded
`pw:browser*`, and the runner removes raw `pw:protocol*`. On failure,
`storybook-browser-diagnostics.log` preserves every attempt summary and the bounded output tail
inside a 1 MiB cap. See the [Storybook diagnosis reference](testing/storybook/README.md) for
`bootstrapStage` interpretation and the upstream issue-filing evidence checklist.

A backend unit shard that fails with `Worker exited unexpectedly` after every test passed (#8259)
is a `teardownTimeout` race, not a genuine worker crash, and no transient-retry rule reruns it: the forks-pool main process closes ~7 Valkey/PSQL/glide-mq sockets in
`test-helpers/vitest.setup.data-stores.mts` `teardown()` after every test passes, and that close is
also the only socket-leak tripwire — see
[Graceful Shutdown § Test Teardown](../overview/architecture/graceful-shutdown.md#test-teardown).
Under the retired self-hosted runners' CPU contention the close occasionally missed the previous 5s
`teardownTimeout` and was force-killed mid-close, which the forks pool then misreports as
`Worker exited unexpectedly`. `vitest.config.mts`'s root-only `teardownTimeout` is now `20_000` for
contention headroom; a genuine hang still force-kills at that ceiling. On any trip,
`[vitest-teardown] phase=… start/done ms=…` lines from `teardown()` plus a `[vitest-teardown-overrun]`
process/handle snapshot from the teardown-overrun reporter's `onProcessTimeout()` name which phase was
still in flight. That vocabulary is deliberately neutral — it must never contain a substring
`hasBackendUnitVitestFailure` (`ci/transient-retry/runner-shutdown-fingerprints.mts`) reads as a
real failure, which `runner-shutdown-safety-regressions.test.mts` regression-tests.

The main-process tripwire above says nothing about a handle a **test** leaks inside a forks-pool
fork: each fork runs many test files sequentially in one OS process, then is force-killed at pool
teardown with any leaked in-fork handle still open, silently masking it (#8278).
`test-helpers/vitest.setup.fork-leak-detection.mts` closes that gap with a per-fork, per-test
`afterEach` growth-delta tripwire — see
[Graceful Shutdown § Fork-Side Leak Detection](../overview/architecture/graceful-shutdown.md#fork-side-leak-detection)
for the mechanism. A confirmed leak throws in the hook and fails that test with a
`[vitest-fork-leak]` block naming the type, baseline, current count, streak, file where the
streak tripped, and file with the largest observed growth step; set
`VITEST_FORK_LEAK_DETECTION=off` to disable it for a run where the heuristic misfires.

A separate, root-level `afterEach` in `test-helpers/vitest.setup.fake-timer-guard.mts` guards a
different shared-state hazard: a test that leaves `vi.useFakeTimers()` installed corrupts every later
test sharing the same fork (`isolate: false`) or file (`isolate: true`), which twice reached CI as a
real incident (#8328, #8330) before either the shared fork-leak hook or an individual test was fixed
one call site at a time. See
[Test Docs § Fake timers must be restored after every test](reference-tests-parallel-safety-and-test-root-hygiene.md#fake-timers-must-be-restored-after-every-test)
for the mechanism and the fix. Set `VITEST_FAKE_TIMER_GUARD=off` to disable it for a run where the
heuristic misfires.
