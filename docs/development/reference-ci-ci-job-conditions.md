# CI Job Conditions

[Back to CI Reference](ci.md#ci-job-conditions)

The pre-merge CI orchestrator starts on every PR (any base branch, including stacked PRs),
merge-group request, and manual dispatch, then lets `detect-changes` decide
which reusable workflows should run. A job starts when its area path filter matches a
non-docs-only change. On PRs, a `.github/workflows/**` or `.github/actions/**` edit sets
`workflow-action-changes` and starts every otherwise eligible job; merge groups start every Vitest
job; on manual dispatch, any `workflow-action-changes` value other than `false` starts every job.
Each started job runs its full suite; see [area test suites](ci.md#area-test-suites).
Path-scoped `main-*` workflows own main tests. A trusted completed-run receiver dispatches successful
source metadata to private infrastructure, which owns artifact builds and publication. Static Code Analysis runs
directly on every main push. Keep PR gating at job level instead of
top-level `paths-ignore`: the fan-in jobs need to report skipped checks consistently, and
workflow-owned docs such as `.github/workflows/README.md`, `.github/workflows/WORKFLOWS.md`, and `.github/workflows/AUTHORING.md` are test fixtures
that must still run the tooling suite. `detect-changes` `shell-scripts` is initialize-smoke input
(`dev/initialize*`, `dev/lib/**`, `dev/host-storage-preflight.mts`, `dev/worktree-port-policy.json`,
and `**/*.sh`), not every file under `ci/` or `dev/`. PR `test-portability` uses a dedicated
`portability` filter. On `main`, `main-checks.yml` still starts from its union path list, then
`select-main-checks` starts only the matching suite.

Only static-analysis failures suppress downstream work. Each test, both Playwright suites, and each
Docker validation build waits on `static-code-analysis` and its area static checks, never on
another test, so PR, merge-group, and manual runs all execute them in parallel. The required
`tests` and `build` fan-in checks still report every failure.

The backend Dockerfile copies the root and required workspace manifests before one filtered
`pnpm install --ignore-scripts && pnpm rebuild --pending` layer. The web Dockerfile follows the same
single-layer pattern for the declared `web...` dependency closure. Do not add a separate
`pnpm fetch` pass to either image: BuildKit cache mounts are not restored by the exported layer cache
on ephemeral runners, and fetch also runs package lifecycle scripts before the filtered install
recreates `node_modules`, duplicating native downloads and snapshot work. Source files remain below
each dependency layer, so source-only changes still reuse it during PR validation. Runtime image
targets, publication, retention, and live worker placement are private-infrastructure configuration.
PR validation builds use one shared `max-parallelism = 3` BuildKit setting. Treat the 8-arm PR
runner as the limiting environment; if it produces a confirmed
BuildKit OOM/EOF, restore the single shared value to 2 rather than assigning branch-specific limits.
