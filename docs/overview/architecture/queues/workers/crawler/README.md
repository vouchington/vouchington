# Crawler Worker

Source entrypoint: [backend/workers/crawler/README.md](../../../../../../backend/workers/crawler/README.md)

Worker package for URL crawl jobs.

URL result shaping and retry/error handling live in
[processor outcomes](../../../../../../backend/workers/crawler/processors/outcomes.mts),
which the job dispatcher imports directly. The outcome tests keep real URL, rate-limit and queue
ownership while exercising the same handlers used by the worker.

## Exports

- `crawlUrls` - worker instance for the `crawl_urls` queue.

## Durable transition matrix

The `crawl_url` job fetches an external host and writes a `crawls` row (and the raw body to S3). A
rate-limited run records the 429 in `crawls` and, when `Retry-After` is present and fewer than 3
replacements have run, enqueues the next replacement, as described in the
[queue README](../../crawler/README.md). The rows below cover that replacement chain; the
scheduled crawl dispatchers in [crawling architecture](../../../crawling.md#url-crawl-routing-and-exclusivity)
re-select URLs from PostgreSQL.

| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dispatch failure                                   | The replacement add throws, or returns no job because an equivalent replacement holds the dedup id. The job fails with `Rate-limited crawl <urlId> was not re-enqueued for retry <n>` and carries the rate-limit error as its cause. | GlideMQ retries the job (3 attempts, exponential 5 s backoff). If every attempt fails, the scheduled crawl dispatchers pick the URL up on a later pass.                             | Per-retry debounce id `crawl_url_ratelimit__<urlId>__<n>`                                | `processors.test.mts`: fails the job instead of completing when the rate-limit replacement is skipped. The add-throws branch has no dedicated test.                                                                  |
| Provider non-consumption                           | The host answers 429 with `Retry-After`; the `crawls` row records 429 and the hostname 429 lock is set.                                                                                                                              | The replacement is enqueued with the `Retry-After` delay and the original priority. With no `Retry-After`, or after 3 replacements, the error is thrown to the job's generic retry. | Per-retry dedup id; the per-hostname `ordering.rateLimit` paces replacements             | `processors.test.mts`: re-enqueues rate-limited URLs until the processor circuit breaker trips; routes rate-limit preflight errors through the processor error handler                                               |

| Durable commit followed by reply loss              | The replacement job exists but the original job's completion was lost (stall or crash after the add).                                                                                                                                | GlideMQ redelivers the original job. Its add is skipped because the replacement holds the id, so it throws and retries until its attempts are spent. The replacement still runs.    | Per-retry dedup id                                                                       | Same code path as the dispatch-failure test above; no test redelivers the job.                                                                                                                                       |

| TTL expiry                                         | The debounce TTL is `max(rateLimitMs, delay)`; GlideMQ retention (100 completed, 100 failed) evicts job records.                                                                                                                     | After the TTL a duplicate enqueue is accepted. It costs one extra fetch, paced by the hostname `ordering.rateLimit`; no state lives in the job record.                              | Re-crawling a URL is the normal scheduled operation, so a duplicate crawl is repeat-safe | `enqueues.test.mts`: keeps bulk crawl jobs deduplicated by URL                                                                                                                                                       |
