# User Deletions Worker

Source entrypoint: [backend/workers/user-deletions/README.md](../../../../../../backend/workers/user-deletions/README.md)

The IO worker processes one fenced, bounded account-deletion batch per delivery. A committed batch
returns the next persisted attempt for enqueue; if enqueue fails, the queue's recovery dispatcher
finds the durable unfinished request and resumes it.

On a terminal GlideMQ attempt failure inside the batch, the worker passes that boundary to the
lifecycle service, which rotates the persisted token before the failed job is retained. A failure
before the claim, a job that stalls past its limit, and an early return leave the token unchanged.
Recovery therefore keeps an unstarted token, so an existing queued job remains the canonical
delivery, and `enqueueOrReactivateBulkUserDeletions` removes a completed or failed record under that
job ID before it adds the attempt again. A waiting, delayed, or active job under the ID is never
touched, so a delayed successor keeps its `retryAfterMs` delay.

Concurrency is fixed at two so independent deletions can progress without multiplying database lock
pressure. Provider cleanup is retried from durable work rows and must complete before the internal
deletion request is finalized.
