# Agent Session Hooks

[Back to Dev Environment Reference](README.md#agent-session-hooks)

Every hook entrypoint reads its stdin payload through `dev/codex-hooks/hook-payload.mts`
(`readHookPayload`, `extractToolCommand`, and the tool-name, session-id, file-path, and runtime
helpers). That module has no policy imports, so non-policy hooks never load the PreToolUse policy.
`readHookPayload` also maps Cursor's Claude-compat dialect to Claude's through
`dev/codex-hooks/cursor-payload.mts`: tool `Shell` becomes `Bash`, and its `tool_output` JSON
string `{exitCode, output}` becomes `tool_response` `{exit_code, stdout}`.
Cursor and Grok run the `.claude/settings.json` hooks below through Claude-compat.

- **`./dev/check-fresh-base`** — SessionStart hook (Claude Code + Codex): fetches `origin/main`, then reports the branch name, clean/dirty state, and whether HEAD is ahead, behind, or diverged. A clean matching branch exits silently. Missing refs and fetch failures report that freshness is unknown instead of silently trusting cached state. Its guidance distinguishes new work from resumed work and never infers `--force`; the reset-or-rebase decision is made after Plan Mode. Set `CHECK_FRESH_BASE_SKIP_FETCH=1` to skip the network fetch (used by tests). Outputs raw JSON (hook format) when run manually. See [Fresh-base planning](../docs/development/README.md#fresh-base-planning).
- **`./dev/check-web-init`** — SessionStart hook (Claude Code + Codex): nudges `./dev/initialize web` when `.initialized` is absent or not `"web"` from the worktree root, reminding the agent to run `./dev/initialize web` then `./dev/tmux` before UI/browser work. Exits silently when `.initialized` = `"web"`, on `compact` restart, or outside a git repo.
- **`node dev/codex-hooks/persist-session-id.mts claude`** — SessionStart hook (Grok and Cursor
  Claude-compat only): no-ops unless the runtime resolves to `grok` or `cursor`, then persists
  `.local/grok-session-id` or `.local/cursor-session-id` from the real hook id, or generates
  `<agent>-` + UUID when neither a payload id nor a valid persist file exists. Silent stdout. See
  [agent-harness-parity.md](../docs/development/agent-harness-parity.md).
- **`node dev/check-blackboard.mts`** — SessionStart hook (Claude Code + Codex): probes the hosted agent-blackboard deployment with `sessions list --limit 1` — a single bounded page that verifies the server, DynamoDB, and token in one round trip without draining the full sessions table. Exits silently when the probe succeeds, on `compact` restart, or outside a git repo. On failure, emits a stop-work directive: agent-blackboard is a hard session prerequisite (journaling, retrospectives, and distillation all depend on it), so the agent should halt and tell the user to verify `AGENT_BLACKBOARD_URL`/`AGENT_BLACKBOARD_TOKEN` are exported and valid before proceeding. Set `CHECK_BLACKBOARD_SKIP=1` to skip the probe (used by tests). Inside the Claude Code sandbox (`SANDBOX_RUNTIME` set), it instead emits a "probe skipped, not an outage" context note — the sandbox denies `AGENT_BLACKBOARD_TOKEN` and blocks egress, so a sandboxed run can't distinguish a real outage from a withheld credential. This is advisory only — the actual mid-session enforcement is that `dev/blackboard-journal.mts` and friends hard-fail with no filesystem fallback. See [agent-blackboard](../docs/development/agent-blackboard.md).
- **`node dev/codex-hooks/pre-tool-use.mts <claude|codex>`** — PreToolUse policy hook (Claude Code, Codex, Grok, and Cursor through Claude-compat). A block exits 2 with its reason on stderr and writes a runtime-compatible deny payload to stdout. It is a guardrail, not a security boundary; see the [hook threat model](../docs/development/agent-sandbox.md#hook-threat-model). Session `hookCwd` (`tool_input.cwd` / `workdir`, payload `cwd` / `workspaceRoot`, else `process.cwd()`) is the base working directory. Sequential command-local `cd` on the inspected command, then the invocation's own `env -C` / `--chdir` wrappers, is the per-invocation cwd for relative `--body-file` and `gh-merge-base`. A `cd` run through a non-builtin wrapper (`env cd`, `nohup cd`) changes nothing, and an unresolvable `env -C` target leaves the cwd unknown; an explicit `--base` / `-B` (and `gh stack init --base` / `-b`) is still checked then, and only the checks that read the checkout are skipped: the `gh-merge-base` fallback and `gh stack init`'s HEAD-ancestry guard. See #10897. The entrypoint also injects the session checkout's home GitHub owners (`sessionHomeOwners` in `policy/github-checkout-owners.mts`, read lazily from `git remote -v`, `gh repo set-default`, and the root `package.json` `repository`, so a fork-only checkout still counts its declared upstream), so the PR and issue content rules skip a command that provably targets a repository outside them; merge authority and the `gh stack` policy never read it. Without a literal `--repo`, gh's own prefix may only set or unset variables (`VAR=x`, `env`, `env -u`; not `env -i`, `env -C`, or another wrapper), and the inherited `GH_REPO` and cwd remotes count as proof only for a top-level gh reached through nothing but `&&`-joined literal `cd`s with no `GIT_*` prefix. A nested `bash -c`, heredoc, or `$(…)` body, or any other command or joiner before gh (a short-circuited or pipelined `cd`, `builtin`/`eval`/function `cd`, `pushd`, a same-command `git remote set-url` or `gh repo set-default`), needs a literal `--repo` or `GH_REPO` prefix. Those home owners and cwd remotes come from mutable checkout state that the protected-hook-paths guard doesn't cover. That is accepted, because the content rules are conventions, not a security boundary, and the merge rules never read them. See #434.
- **`node dev/journal-checkpoint.mts compact [claude|codex]`** — SessionStart hook (Claude Code, Codex, and the Grok/Cursor Claude-compat runtimes), gated to the `compact` restart source: reads the transcript identified by the hook payload, computes the same facts as `pnpm exec vouchington retrospective-transcript`, and appends them as a real `type:"journal"` agent-blackboard entry — the mechanical post-compaction checkpoint from #9337, replacing what used to be only a printed reminder. The optional runtime argv is the same contract as `pre-tool-use.mts` (`claude` from `.claude/settings.json`, `codex` from `.codex/config.toml`); the payload and runtime markers resolve Grok or Cursor before the `claude` argv token is trusted. Compact also classifies a Codex rollout transcript path as `codex` when the hook child omits `CODEX_THREAD_ID`. Any other SessionStart source exits immediately without importing the transcript or blackboard modules.
- **`node dev/codex-hooks/post-tool-use-command.mts <claude|codex>`** — the single merged PostToolUse hook (Claude Code, Codex, and the Grok/Cursor Claude-compat runtimes), registered once on the `ExitPlanMode|Bash|run_terminal_command`/`ExitPlanMode|Bash` matcher group. It replaces what used to be three separately-spawned Codex hook processes (four on Claude Code) firing on the same tool call — Codex's single shell tool always serializes as `tool_name: "Bash"`, and `is_exact_matcher()` treats that matcher as exact alternation, so it matched ~77% of Codex tool calls. The entrypoint reads stdin and parses the hook payload exactly once, then runs every side effect in-process, each behind its own try/catch so one failing step never skips another: the tmux checkpoint reminder (`dev/tmux-reminder-post-tool.mts`'s `renderPostToolReminder`, ported from `tmux-agent-reminder`'s old `post-tool` case — see that script's own comment), the journal-checkpoint tool pipeline (`runToolCheckpoint`, below), and the session-friction recorder (`recordFriction`, below). Only the tmux reminder may write stdout, and it writes at most once, at the very end, so a partial or doubled hook response is impossible. Fail-open throughout: any error anywhere in the chain is swallowed and the process always exits 0.
- **`dev/journal-checkpoint/tool.mts`'s `runToolCheckpoint`** — the PostToolUse half of the #9337 mechanical journal trigger, invoked in-process by the merged hook above for both Claude Code and Codex (Codex's payload shape is now confirmed: `tool_input = {command}` only, `tool_response` is a plain truncated merged-output _string_ with no exit code — `codex-rs/core/src/tools/context.rs:363`). It cheaply pattern-matches the payload against two checkpoints and only imports the blackboard client once one actually matches, so the common case (neither checkpoint fires) stays close to zero extra cost beyond the match itself. The runtime argv is required for Codex identity on this event because PostToolUse has no transcript path. Checkpoint 2 (repeated failure capture) tracks high-signal test/lint/CI command failures (`vitest`, `playwright`, `no-mistakes`, `tsgo`, `oxlint`, `gh run`, `pr-shepherd`) in a session+worktree-scoped counter file under `tmpdir()` (12h TTL) and journals every 3rd one, with the last 3 failures' command and truncated stderr — **Claude-only**: Codex has an `exit_code` on `ExecCommandToolOutput` but never forwards it to hooks (`context.rs:369-377` returns only the output string), so there is no reliable failure signal to key on for Codex tool calls. Checkpoint 3 (PR/push milestones) matches `gh pr create`/`git push` on both runtimes, accepting either a Claude-shaped `success` outcome (object `tool_response`) or a Codex-shaped `output` outcome (string `tool_response`), only when the tool output corroborates success (a PR URL for `gh pr create`; a non-rejected ref-update line for `git push`) — a completed-but-rejected push does not journal. Both checkpoints share one fail-open contract: any error (missing credential, network failure, sandboxed run, stale session) is swallowed and never surfaces as hook noise, a blocked tool call, or added latency beyond a ~10s worst-case per-append timeout (two sequential 5s timeouts in `append.mts`) — in contrast to `dev/blackboard-journal.mts`'s agent-initiated `append`, which hard-fails so a human watching the session can react. See [agent-blackboard](../docs/development/agent-blackboard.md).
- **`dev/session-friction/record.mts`'s `recordFriction`** — invoked in-process by the merged PostToolUse hook above for both Claude Code and Codex. It adapts raw host hook payloads to the hardened `vouchington-tooling/session-friction` recorder, which classifies `sandbox-escalation` and `sandbox-failure` observations and writes a bounded private log with an opaque hashed filename under `${TMPDIR:-/tmp}/voucha-session-friction-v2/`. The v2 namespace deliberately leaves legacy, non-private evidence directories untouched. `sandbox-failure` is **Claude-only**, same documented limit as journal-checkpoint 2 and for the same reason: Codex's `tool_response` is a merged, truncated stdout+stderr string with no exit code, so no content-based match against it can distinguish an incidental echo from a genuine failure; only Claude's object-shaped `tool_response.stderr` is genuine single-command stderr. A generic CI/check failure is deliberately **not** hook-classifiable either and reaches the retrospective through journal entries. The recorder touches the log even when nothing classifies so "hook never ran" and "hook ran with zero friction" stay distinguishable. The hook remains fail-open: errors are swallowed, stdout stays silent, and the exit code is always 0. `node dev/session-friction/report.mts --session-id <id>` combines the shared report builder with Vouchington's hosted journal adapter. See [`dev/session-friction/`](reference-command-catalog.md#read-only-helpers).
- **`node dev/session-friction/record.mts permission-request`** — Codex-only `PermissionRequest` hook (`codex-rs/hooks/src/schema.rs`'s `HookEventNameWire::PermissionRequest`), the sole way to recover a sandbox-escalation signal on Codex: its PostToolUse `tool_input` is `{command}` only, with no `with_escalated_permissions` field to key on, so the event _firing at all_ is the signal — no field inspection needed. Calls `recordPermissionRequestFriction`, which classifies with `detail: 'permission-request'` only when the event's own `tool_name` is Codex's one shell tool (always the literal `"Bash"`, `HookToolName::bash()`) and a command can be extracted — this excludes a non-shell approval prompt (an MCP tool, a file write outside the workspace) whose `tool_input` might otherwise happen to carry its own `command`-shaped field, which would misrecord as a shell sandbox escalation that never occurred. The recorded detail is deliberately distinct from the `dangerouslyDisableSandbox=true`/`with_escalated_permissions=true` details above, since a requested escalation may still be denied, whereas those two mean the escalated command actually ran. Registered with no `matcher` (Codex's `PermissionRequest` schema allows a catch-all group, matching the existing no-matcher style of `SessionStart`). Emits no stdout, so it cannot and does not alter the approval decision — every field on `PermissionRequestCommandOutputWire`/`PermissionRequestHookSpecificOutputWire` is optional/serde-default, so an empty response is a pure no-op observation.

Codex hooks consume their explicit payload `session_id` directly and never write the root-only
`.local/codex-session-id`: hook metadata cannot distinguish an interactive root from a spawned
Codex child. The interactive root CLI uses `--root-codex` and, once for an absent-thread new
session, `--new-root-codex-session`; children never use either flag.
