# Agent Session Hooks

[Back to Dev Environment Reference](README.md#agent-session-hooks)

- **`./dev/check-fresh-base`** — SessionStart hook (Claude Code + Codex): fetches `origin/main`, then reports the branch name, clean/dirty state, and whether HEAD is ahead, behind, or diverged. A clean matching branch exits silently. Missing refs and fetch failures report that freshness is unknown instead of silently trusting cached state. Its guidance distinguishes new work from resumed work and never infers `--force`; the reset-or-rebase decision is made after Plan Mode. Set `CHECK_FRESH_BASE_SKIP_FETCH=1` to skip the network fetch (used by tests). Outputs raw JSON (hook format) when run manually. See [Fresh-base planning](../docs/development/README.md#fresh-base-planning).
- **`./dev/check-web-init`** — SessionStart hook (Claude Code + Codex): nudges `./dev/initialize web` when `.initialized` is absent or not `"web"` from the worktree root, reminding the agent to run `./dev/initialize web` then `./dev/tmux` before UI/browser work. Exits silently when `.initialized` = `"web"`, on `compact` restart, or outside a git repo.
- **`node dev/codex-hooks/persist-grok-session-id.mts`** — SessionStart hook (Grok Claude-compat only):
  no-ops unless `GROK_SESSION_ID` or `GROK_HOOK_EVENT` is set, then persists `.local/grok-session-id`
  from the real hook id or generates `grok-` + UUID when neither a payload id nor a valid persist
  file exists. Cursor CLI uses a separate `.local/cursor-session-id` path. Silent stdout. See
  [agent-harness-parity.md](../docs/development/agent-harness-parity.md).
- **`node dev/check-blackboard.mts`** — SessionStart hook (Claude Code + Codex): probes the hosted agent-blackboard deployment with `sessions list --limit 1` — a single bounded page that verifies the server, DynamoDB, and token in one round trip without draining the full sessions table. Exits silently when the probe succeeds, on `compact` restart, or outside a git repo. On failure, emits a stop-work directive: agent-blackboard is a hard session prerequisite (journaling, retrospectives, and distillation all depend on it), so the agent should halt and tell the user to verify `AGENT_BLACKBOARD_URL`/`AGENT_BLACKBOARD_TOKEN` are exported and valid before proceeding. Set `CHECK_BLACKBOARD_SKIP=1` to skip the probe (used by tests). Inside the Claude Code sandbox (`SANDBOX_RUNTIME` set), it instead emits a "probe skipped, not an outage" context note — the sandbox denies `AGENT_BLACKBOARD_TOKEN` and blocks egress, so a sandboxed run can't distinguish a real outage from a withheld credential. This is advisory only — the actual mid-session enforcement is that `dev/blackboard-journal.mts` and friends hard-fail with no filesystem fallback. See [agent-blackboard](../docs/development/agent-blackboard.md).
- **`node dev/codex-hooks/pre-tool-use.mts <claude|codex>`** — PreToolUse policy hook (Claude Code, Codex, Grok Claude-compat, Cursor before-shell). Session `hookCwd` (`tool_input.cwd` / `workdir`, payload `cwd` / `workspaceRoot`, else `process.cwd()`) is the base working directory. Sequential command-local `cd` on the inspected command is the per-invocation cwd for closing-ref `gh repo view`, relative `--body-file`, and `gh-merge-base`. `--repo` / `GH_REPO` remain repo-identity overrides; qualified `owner/repo#N` remains a workaround. See #10897. The entrypoint also injects the session checkout's GitHub owner (`checkoutOwner` in `policy/github-content-rule-scope.mts`, read lazily from `git remote -v` plus `gh repo set-default`), so the PR and issue content rules skip a command that provably targets another owner's repository; merge authority and the `gh stack` policy never read it. See #434.
- **`node dev/journal-checkpoint.mts compact [claude|codex]`** — SessionStart hook (Claude Code + Codex), gated to the `compact` restart source: reads the transcript identified by the hook payload, computes the same facts as `node dev/retrospective-transcript-facts.mts`, and appends them as a real `type:"journal"` agent-blackboard entry — the mechanical post-compaction checkpoint from #9337, replacing what used to be only a printed reminder. The optional runtime argv is the same contract as `pre-tool-use.mts` (`claude` from `.claude/settings.json`, `codex` from `.codex/config.toml`); Grok Claude-compat still wins via `GROK_SESSION_ID` / `GROK_HOOK_EVENT`. Compact also classifies a Codex rollout transcript path as `codex` when the hook child omits `CODEX_THREAD_ID`. Any other SessionStart source exits immediately without importing the transcript or blackboard modules.
- **`node dev/codex-hooks/post-tool-use-command.mts <claude|codex>`** — the single merged PostToolUse hook (Claude Code + Codex), registered once on the `ExitPlanMode|Bash|run_terminal_command`/`ExitPlanMode|Bash` matcher group. It replaces what used to be three separately-spawned Codex hook processes (four on Claude Code) firing on the same tool call — Codex's single shell tool always serializes as `tool_name: "Bash"`, and `is_exact_matcher()` treats that matcher as exact alternation, so it matched ~77% of Codex tool calls. The entrypoint reads stdin and parses the hook payload exactly once, then runs every side effect in-process, each behind its own try/catch so one failing step never skips another: the tmux checkpoint reminder (`dev/tmux-reminder-post-tool.mts`'s `renderPostToolReminder`, ported from `tmux-agent-reminder`'s old `post-tool` case — see that script's own comment), the journal-checkpoint tool pipeline (`runToolCheckpoint`, below), and the session-friction recorder (`recordFriction`, below). Only the tmux reminder may write stdout, and it writes at most once, at the very end, so a partial or doubled hook response is impossible. Fail-open throughout: any error anywhere in the chain is swallowed and the process always exits 0.
- **`dev/journal-checkpoint/tool.mts`'s `runToolCheckpoint`** — the PostToolUse half of the #9337 mechanical journal trigger, invoked in-process by the merged hook above for both Claude Code and Codex (Codex's payload shape is now confirmed: `tool_input = {command}` only, `tool_response` is a plain truncated merged-output _string_ with no exit code — `codex-rs/core/src/tools/context.rs:363`). It cheaply pattern-matches the payload against two checkpoints and only imports the blackboard client once one actually matches, so the common case (neither checkpoint fires) stays close to zero extra cost beyond the match itself. The runtime argv is required for Codex identity on this event because PostToolUse has no transcript path. Checkpoint 2 (repeated failure capture) tracks high-signal test/lint/CI command failures (`vitest`, `playwright`, `no-mistakes`, `tsgo`, `oxlint`, `gh run`, `pr-shepherd`) in a session+worktree-scoped counter file under `tmpdir()` (12h TTL) and journals every 3rd one, with the last 3 failures' command and truncated stderr — **Claude-only**: Codex has an `exit_code` on `ExecCommandToolOutput` but never forwards it to hooks (`context.rs:369-377` returns only the output string), so there is no reliable failure signal to key on for Codex tool calls. Checkpoint 3 (PR/push milestones) matches `gh pr create`/`git push` on both runtimes, accepting either a Claude-shaped `success` outcome (object `tool_response`) or a Codex-shaped `output` outcome (string `tool_response`), only when the tool output corroborates success (a PR URL for `gh pr create`; a non-rejected ref-update line for `git push`) — a completed-but-rejected push does not journal. Both checkpoints share one fail-open contract: any error (missing credential, network failure, sandboxed run, stale session) is swallowed and never surfaces as hook noise, a blocked tool call, or added latency beyond a ~10s worst-case per-append timeout (two sequential 5s timeouts in `append.mts`) — in contrast to `dev/blackboard-journal.mts`'s agent-initiated `append`, which hard-fails so a human watching the session can react. See [agent-blackboard](../docs/development/agent-blackboard.md).
- **`dev/session-friction/record.mts`'s `recordFriction`** — invoked in-process by the merged PostToolUse hook above for both Claude Code and Codex. It adapts raw host hook payloads to the hardened `vouchington-tooling/session-friction` recorder, which classifies `sandbox-escalation` and `sandbox-failure` observations and writes a bounded private log with an opaque hashed filename under `${TMPDIR:-/tmp}/voucha-session-friction-v2/`. The v2 namespace deliberately leaves legacy, non-private evidence directories untouched. `sandbox-failure` is **Claude-only**, same documented limit as journal-checkpoint 2 and for the same reason: Codex's `tool_response` is a merged, truncated stdout+stderr string with no exit code, so no content-based match against it can distinguish an incidental echo from a genuine failure; only Claude's object-shaped `tool_response.stderr` is genuine single-command stderr. A generic CI/check failure is deliberately **not** hook-classifiable either and reaches the retrospective through journal entries. The recorder touches the log even when nothing classifies so "hook never ran" and "hook ran with zero friction" stay distinguishable. The hook remains fail-open: errors are swallowed, stdout stays silent, and the exit code is always 0. `node dev/session-friction/report.mts --session-id <id>` combines the shared report builder with Vouchington's hosted journal adapter. See [`dev/session-friction/`](reference-command-catalog.md#read-only-helpers).
- **`node dev/session-friction/record.mts permission-request`** — Codex-only `PermissionRequest` hook (`codex-rs/hooks/src/schema.rs`'s `HookEventNameWire::PermissionRequest`), the sole way to recover a sandbox-escalation signal on Codex: its PostToolUse `tool_input` is `{command}` only, with no `with_escalated_permissions` field to key on, so the event _firing at all_ is the signal — no field inspection needed. Calls `recordPermissionRequestFriction`, which classifies with `detail: 'permission-request'` only when the event's own `tool_name` is Codex's one shell tool (always the literal `"Bash"`, `HookToolName::bash()`) and a command can be extracted — this excludes a non-shell approval prompt (an MCP tool, a file write outside the workspace) whose `tool_input` might otherwise happen to carry its own `command`-shaped field, which would misrecord as a shell sandbox escalation that never occurred. The recorded detail is deliberately distinct from the `dangerouslyDisableSandbox=true`/`with_escalated_permissions=true` details above, since a requested escalation may still be denied, whereas those two mean the escalated command actually ran. Registered with no `matcher` (Codex's `PermissionRequest` schema allows a catch-all group, matching the existing no-matcher style of `SessionStart`/`PreCompact`). Emits no stdout, so it cannot and does not alter the approval decision — every field on `PermissionRequestCommandOutputWire`/`PermissionRequestHookSpecificOutputWire` is optional/serde-default, so an empty response is a pure no-op observation.

Codex hooks consume their explicit payload `session_id` directly and never write the root-only
`.local/codex-session-id`: hook metadata cannot distinguish an interactive root from a spawned
Codex child. The interactive root CLI uses `--root-codex` and, once for an absent-thread new
session, `--new-root-codex-session`; children never use either flag.
