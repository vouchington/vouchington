# Storybook — Reference

CI-failure diagnosis and key files for `web/storybook/`. For imperative story-authoring rules, see [CLAUDE.md](CLAUDE.md).

## Diagnosing CI failures

- **Silent browser startup or stalled Storybook modules** — `ci/storybook-browser-runner.mts` owns one monotonic 300-second session budget across at most three attempts, while Vitest's browser connection deadline uses the same `STORYBOOK_BROWSER_HANG_MS` value as the runner's 120-second pre-test hang threshold. Each eligible retry waits for the previous Vitest/Chromium process group to close, then starts a new process group on a distinct browser API port. Once the `vitest-storybook-progress-reporter` emits a bounded `module-collected`, `module-start`, or `module-end` marker, a later stall or assertion failure is terminal. Localhost dynamic-module fetch failures and add-on setup-file `Vitest failed to find the runner` before `|web-storybook-browser` output remain retryable even after those module markers. Attempt 1 uses the persistent Vite cache `.cache/vite/storybook-browser` unless `STORYBOOK_BROWSER_PERSISTENT_CACHE=0` disables it or `STORYBOOK_BROWSER_PERSISTENT_CACHE_DIR` overrides the path. Pure browser/session failures reuse the ready Vite cache; optimizer stalls, module-fetch failures, and missing-runner evidence rotate a suspect cache. The runner always captures the low-volume Vitest Playwright milestones and browser request failures, filters Vitest browser-API command noise, and adds bounded `pw:browser*` lifecycle diagnostics only after a prior browser hang. It removes `pw:protocol*`: raw protocol traffic previously produced a 1.73 GB log without showing repository-owned test progress. On failure, download `browser-debug-log-storybook`; `storybook-browser-diagnostics.log` contains all attempt summaries plus a bounded output tail and can never exceed 1 MiB. For faster local fault injection, lower `STORYBOOK_BROWSER_HANG_MS` or `STORYBOOK_BROWSER_SESSION_BUDGET_MS`.
- **`@storybook/addon-vitest` setup file says `Vitest failed to find the runner` before `|web-storybook-browser` output** — this is a browser startup/context race before stories run. Module lifecycle markers (`module-collected` / `module-start` / `module-end`) do not prove a story ran; the runner still treats the fingerprint as `runnerMissing=true`, rotates the suspect Vite cache, and may recycle the whole Vitest/Chromium process within the shared budget. If the same message appears after `|web-storybook-browser` output or with a story import/assertion failure, it is a real failure and must not retry.
- **`Failed to connect to the browser session` before semantic module progress** — this is a pre-test Vitest/Chromium session-handshake failure when Vite already reported `dependencies optimized`. The runner preserves the ready Vite cache and may recycle the whole Vitest/Chromium process within the shared budget. If module progress already started, investigate the specific story or browser error instead.
- **Reading `bootstrapStage` in the diagnostics artifact** — `no-provider-evidence` means no public provider milestone was observed; `launch-or-context`, `context-to-page`, `page-to-navigation`, and `navigation-to-websocket` identify the furthest proven Playwright-provider boundary; `handshake-after-websocket` proves the orchestrator WebSocket connected but does not prove Vitest declared the session ready. `bootstrapTimeline` gives the ordered millisecond offsets, while `orchestratorDisconnectCount`, `requestFailureCount`, and `requestFailureSamples` retain bounded disconnect and failed-request evidence. These stages are advisory: retry eligibility still depends on the stable pre-semantic failure classifiers, not dependency debug wording.
- **Filing the upstream root-cause issue** — describe the repository fix as bounded whole-process recycling around an opaque dependency bootstrap failure, not as a fix for the dependency defect. Include the GitHub run URL and commit, the failed attempt's `bootstrapStage` and complete `bootstrapTimeline`, request-failure samples, and the diagnostics artifact; its `runtime` record supplies the Node, Vitest, Storybook add-on, Vitest Playwright provider, Playwright, and Chromium versions. Provider stages before navigation point toward Vitest's Playwright provider or Playwright/Chromium; failed Storybook/Vite module requests point toward the owning module pipeline; an orchestrator-connected handshake timeout points toward Vitest session readiness. File only after the captured evidence distinguishes the failing boundary.
- **`new dependencies found:` plus `optimized dependencies changed. reloading`** — Vite discovered a published package after the first optimize pass and aborted in-flight Chromium fetches, including `virtual:/@storybook/builder-vite/project-annotations.js`. This is a missing `storybookBrowserOptimizeDeps` include in `test-helpers/vitest-config/storybook-browser-optimize-deps.mts`, not a cache or process-isolation flake. The runner fails that attempt as `optimizerReloadFromNewDeps=true` / `retryable=false` and names the packages. Do not raise `STORYBOOK_BROWSER_STARTUP_ATTEMPTS`. Add the named packages to the include list (bare name or `parent > child`).
- **`Failed to fetch dynamically imported module: …project-annotations.js`** — without the optimizer-reload phrases above, the Vite dev server transiently dropped a fetch of the virtual `project-annotations.js` module. Pre-#5601 logs surfaced this as `setup-file-with-project-annotations.js`; the addon-generated path is no longer fetched. With the current `isolate: false` config the virtual module is imported exactly once per browser session (the ES-module cache deduplicates the import and the global-symbol guard in `vitest.setup.ts` skips re-applying annotations), so this should be extremely rare. If it recurs, the watchdog (`ci/run-storybook-browser-tests.mts`) rotates the suspect Vite cache and retries the whole browser process within the shared session budget, even when earlier stories made semantic progress. If the log also says `Failed to resolve import "storybook/internal/preview-api"`, keep the `web-storybook-browser` alias and preview API warmup in `vitest.config.mts` pointed at `web/node_modules/storybook/dist/preview-api/index.js`. **Do not change `isolate` back to `true`** — that increases the number of virtual-module fetches from 1 to ~119 per run, restoring the flake (each fetch has a small independent chance of being dropped). Do not add a direct `setProjectAnnotations(getProjectAnnotations())` call to `web/.storybook/vitest.setup.ts`; Storybook detects that exact setup-file text and emits a duplicate-annotation warning. Do not warm setup files directly; `vitest.setup.ts` imports custom Storybook mocks and the project annotation setup is wired through `test-helpers/vitest-config/storybook-browser-project.mts`. The workflow allocates `VITEST_STORYBOOK_BROWSER_API_PORT` immediately before starting the runner. Retries retain their port offset and, when rotating a suspect cache, use `vite-storybook-browser-attempt-N` under `RUNNER_TEMP` (with `TMPDIR`/OS-temp fallback). These values do not depend on GitHub run or job identifiers; attempt isolation still prevents collisions within the same job. Local cache paths and the wrapper's process-based port fallback remain unchanged; direct Vitest config leaves an unspecified port unset. Do NOT add `optimizeDeps.entries` (blocks startup in a different way), do NOT add `@/components/…` alias paths to `optimizeDeps.include` (Vite rejects them silently with "Cannot optimize dependency").
- **`No "default" export is defined on the "next/image"` / namespace-object error** — the `next/image` alias for browser mode isn't picking up. Confirm the alias is scoped to the `web-storybook-browser` Vitest project in `vitest.config.mts` so the browser-mode alias does not leak into the published Storybook build.
- **`React.use is not a function` / async component error in browser** — a server component leaked into a story. Add an alias in `web/.storybook/main.ts` `viteFinal.resolve.alias` pointing to a stub under `web/storybook/mocks/`.
- **`userEvent.tab()` leaves focus before an `inert` subtree** — `storybook/test` bundles Testing
  Library's synthetic tab-order calculation, which can select a focusable descendant whose inert
  ancestor makes Chromium reject the focus change. When the story must verify real sequential
  keyboard navigation, dynamically use the supported `vitest/browser` `userEvent.tab()` while
  `globalThis.__vitest_browser__` is present; the Playwright provider sends a native Tab keypress.
  Keep an explicit-focus fallback target so the same play function remains runnable in ordinary
  published/development Storybook, but do not count that fallback as Tab-order coverage. Retain
  focus assertions after both paths, keep the workaround story-scoped, and remove it when
  testing-library/user-event#1215 or storybookjs/storybook#27138 supplies inert-aware tabbing.

## Key files

- `web/.storybook/main.ts` — Storybook + Vite config (server-component aliases, plugin order, pre-bundled deps via `optimizeDeps.include`).
- `web/.storybook/vitest.setup.ts` — stable Storybook project-annotation setup.
- `web/storybook/mocks/` — manual mocks (`next-image.tsx`, `anonymous-structured-data-script.ts`, `assert-proxied-image-src.ts`, `use-turnstile-token.ts`).
- `vitest.config.mts` — `web-storybook-browser` project configuration (browser provider, aliases, `testTimeout`, `hookTimeout`).
